# 后端批量解析重构说明（2026-03-08）

## 1. 重构目标

本次重构只处理“跨节点批量解析”相关代码，不修改既有单条解析语义，不调整 SDK 接口，不引入新的数据库表。

目标如下：

- 降低 `DrirpResolutionService` 的文件体积和职责数量
- 将批量解析的编排逻辑与单条解析逻辑分离
- 保持递归解析与迭代解析两种跨节点模式并存
- 保持现有对外 API 和业务逻辑行为稳定

## 2. 重构后的职责划分

### 2.1 `DrirpResolutionService`

定位：解析门面服务。

职责：

- 暴露单条元数据、对象、资源的分布式解析入口
- 暴露批量元数据、对象、资源的分布式解析入口
- 处理单条 DRIRP 转发消息 `handleResolveForward`
- 将批量 DRIRP 转发消息委托给批量 support 处理

说明：

- 单条解析仍保留在该类中，便于复用既有递归/迭代策略对象
- 批量解析不再直接堆叠在该类中，避免后续继续膨胀

### 2.2 `ResolutionSupport`

定位：单条与批量共用的底层能力支撑。

职责：

- 标识符合法性校验
- 本地解析调用封装
- 下一跳路由解析
- DRIRP 客户端构建与审计记录
- 序列化/反序列化、对象转换、公共辅助方法

### 2.3 `DistributedBatchResolutionSupport`

定位：批量解析专用编排器。

职责：

- 批量请求参数校验
- 按目标节点对标识符分组
- 组织本地解析、递归转发、迭代转发三类流程
- 统一组装元数据 / 数字对象 / 资源的批量返回结果
- 处理 `RESOLVE_BATCH_FORWARD` 协议消息

这样可以让“批量解析”形成独立聚合，不再与单条解析流程交错在同一个大类里。

## 3. 重构后的代码结构

```text
service/
  DrirpResolutionService.java          # 门面，负责单条解析与批量入口委托
  resolve/
    ResolutionSupport.java             # 公共底层能力
    IterativeResolutionStrategy.java   # 单条迭代解析
    RecursiveResolutionStrategy.java   # 单条递归解析
    DistributedBatchResolutionSupport.java  # 批量解析编排
```

## 4. 批量解析内部流程

### 4.1 外部 REST 调用

- Controller 接收 `List<String>` 标识符数组
- Service 做空值校验后，委托 `DrirpResolutionService`
- `DrirpResolutionService` 再委托 `DistributedBatchResolutionSupport`

### 4.2 support 内部处理步骤

1. 校验批量长度是否为空、是否超过上限 `200`
2. 对每个标识符做 trim、格式校验、目标节点提取
3. 将合法条目按 `targetNodeCode` 分组
4. 对每一组执行以下之一：
   - 本地解析
   - 递归跨节点解析
   - 迭代跨节点解析
5. 将各组结果按原始输入顺序回填
6. 统一转换为外部 DTO：
   - `BatchResolveMetadataResponse`
   - `BatchResolveDigitalObjectResponse`
   - `BatchResolveResourceResponse`

## 5. 为什么这样拆分

### 5.1 低耦合

拆分前：

- 单条解析、批量解析、转发协议、结果映射全部堆在 `DrirpResolutionService`
- 修改批量逻辑时容易影响单条逻辑阅读与维护

拆分后：

- 单条解析继续围绕 `ResolutionStrategy`
- 批量解析围绕 `DistributedBatchResolutionSupport`
- 两者只共享 `ResolutionSupport` 的底层能力

### 5.2 高内聚

批量 support 内部只关心四件事：

- 分组
- 转发
- 聚合
- 映射

这比让门面类同时管理协议、路由、分组、结果组装更清晰。

### 5.3 对业务逻辑影响小

- 没有修改本地 SDK 调用方式
- 没有修改节点路由规则
- 没有修改 TTL、visitedUrls、loop detection 的既有语义
- 没有覆盖原有本地批量元数据接口

因此，本次重构属于“结构性重构”，不是“业务行为重构”。

## 6. 新增批量接口

本次配套新增两个 REST 接口：

- `POST /api/v2/identifiers/resolve/batch/object/distributed`
- `POST /api/v2/identifiers/resolve/batch/component/distributed`

其 service/controller 只做薄委托，不承载批量编排逻辑。

## 7. 对论文/答辩可强调的点

可以将本次设计概括为：

- 在既有单条跨节点解析框架上，扩展出面向批处理的统一编排层
- 通过“门面 + 公共 support + 批量 support”的方式实现低耦合重构
- 在不改变核心业务语义的前提下，支持元数据、对象、资源三类结果统一批量解析
- 同时兼容递归解析与迭代解析两种模式，便于实验对比

## 8. 风险与后续建议

当前已解决：

- 批量对象解析
- 批量资源解析
- 批量内部 DRIRP 协议统一携带 `resolveType`
- 结果按输入顺序返回

建议后续继续补充：

- 批量转发链路的审计字段细化
- 多节点联调压测
- 批量失败原因统计与监控指标
- 时序图与类图整理，用于论文正文和答辩 PPT
