# 资源共享能力增强最小侵入修改设计文档（低数据库改动版）

日期：2026-03-09  
适用项目：`dris-enterprise-backend-v2`、`dris-java-sdk`

## 1. 文档目标

本文档用于在尽量不改动现有数据库表结构的前提下，完成以下三类能力增强：

1. 上传完成时增加实体存在校验，保证共享资源真实可用。
2. 为资源增加版本治理能力，避免重复上传导致历史不可追踪。
3. 明确 `resource / tool / service` 三类组件的绑定方式和下载/调用语义。

本版设计强调“最小侵入”原则：

- 尽量不修改现有 `upload_session`、`resource` 表结构。
- 尽量不改动 `dris-java-sdk` 对外模型定义。
- 尽量复用现有 `extra_json` 和现有接口。
- 将新增能力主要通过“新增一张历史表 + 少量代码逻辑调整”完成。

## 2. 设计约束与原则

### 2.1 约束

当前系统已经形成以下真实链路：

1. 标识注册
2. 创建上传会话
3. 客户端上传对象到对象存储
4. 调用 `completeUpload`
5. 资源绑定到 `resource` 当前快照
6. 解析组件或生成下载地址

同时，系统也已经支持另一条链路：

1. 调用 `PUT /api/v2/identifiers/{identifier}/component`
2. 直接绑定 `Resource`
3. 落库到 `resource`

因此，本次改造不应把所有组件都强行纳入上传流程，而应保留“上传型绑定”和“直连型绑定”两条路径。

### 2.2 原则

1. `resource` 表继续表示“当前生效组件快照”。
2. 历史版本不塞进当前表，通过新增历史表保存。
3. 上传校验结果、绑定来源、版本号等附加治理信息优先写入 `extra_json`。
4. `service` 和部分 `tool` 不要求经过对象存储上传。
5. 对外 API 路径尽量不变，只调整行为约束。

## 3. 现状分析

## 3.1 现有表结构

当前关键表如下：

### `upload_session`

已有字段：

- `upload_id`
- `identifier`
- `component_type`
- `bucket`
- `object_key`
- `upload_mode`
- `expected_size`
- `expected_sha256`
- `status`
- `expires_at`
- `extra_json`

### `resource`

已有字段：

- `identifier`
- `component_type`
- `role`
- `storage_type`
- `access_method`
- `content_type`
- `format`
- `locator`
- `size_bytes`
- `hash_value`
- `etag`
- `version_id`
- `created_at`
- `extra_json`

结论：

- `upload_session` 其实已经具备执行“对象是否存在、大小是否一致、摘要是否一致”校验所需的核心字段。
- `resource` 其实已经能表达“当前绑定组件”的主体信息。
- 当前真正缺的是“历史版本保存能力”和“绑定语义收敛”，不是必须先大规模改旧表。

## 3.2 当前存在的问题

### 问题一：`completeUpload` 缺少实体存在校验

当前上传完成时，系统会根据 `upload_session` 直接构建 `Resource` 并写入 `resource`，但未校验：

- 对象存储中是否真的存在该对象
- 实际大小是否等于 `expected_size`
- 若声明了 `sha256`，实际摘要是否一致

这会导致：

- 标识已经绑定资源，但对象可能不存在
- 文件可能为空或大小错误
- 元数据与实体不一致

### 问题二：重复上传会覆盖对象路径，历史不可追踪

当前 `objectKey` 生成方式按标识固定，例如：

- `identifiers/{identifier}/resource`
- `identifiers/{identifier}/tool`
- `identifiers/{identifier}/service`

这意味着重复上传时，本质是覆盖而不是形成独立历史版本。

### 问题三：三类组件的绑定路径不够清晰

目前系统虽然在 `DrisBusinessRules` 中已经对三类组件做了基础区分，但接口层面仍存在混用：

- `service` 目前也能创建上传会话
- `service` 的真实语义其实是绑定 API 入口，而不是上传一个可下载对象
- `tool` 既可能是对象存储中的工具包，也可能是本地执行描述

## 4. 最小侵入总体方案

本次改造采用以下策略：

1. 不修改现有 `upload_session` 表结构。
2. 不修改现有 `resource` 表结构。
3. 新增一张 `resource_version` 历史表。
4. 版本号、来源上传会话、校验状态等扩展治理信息，优先写入 `resource.extra`。
5. 上传校验细节优先写入 `upload_session.extra`。
6. `service` 和 `tool(local_exec)` 改为直接绑定，不再要求上传会话。

这套方案的核心是：

- 旧表继续承担当前流程
- 新能力放到新表和 `extra_json`
- 降低 SQL、Repository、DTO、历史数据迁移的改造量

## 5. 为什么不改 `upload_session` 和 `resource`

## 5.1 不改 `upload_session` 的原因

如果给 `upload_session` 再加：

- `actual_size`
- `actual_hash`
- `verify_status`
- `verify_message`
- `completed_at`

虽然查询会更方便，但会带来：

1. `schema.sql` 变更
2. JDBC Repository 读写 SQL 变更
3. 测试数据和兼容迁移变更
4. 旧数据处理逻辑变更

而实际上：

- 现有 `bucket/object_key/expected_size/expected_sha256/status/expires_at` 已足够完成上传校验。
- 校验结果可以直接写入 `extra_json`，例如：

```json
{
  "profile": "resource-file",
  "filename": "a.csv",
  "_verifyStatus": "VERIFIED",
  "_verifyMessage": "ok",
  "_actualSize": 1024,
  "_actualHash": "sha256:xxxx",
  "_completedAt": "2026-03-09T10:00:00Z"
}
```

因此，最小侵入方案中，`upload_session` 不做表结构修改。

## 5.2 不改 `resource` 的原因

如果给 `resource` 再加：

- `bucket`
- `object_key`
- `version_no`
- `source_upload_id`
- `verify_status`
- `last_verified_at`

虽然更利于直接 SQL 查询，但也会导致：

1. `resource` 表变更
2. 所有 `SELECT / INSERT / UPDATE` SQL 变更
3. 旧数据回填问题
4. SDK 当前 `Resource` 模型与数据库映射需要联动调整

而实际上：

- `resource` 表本来就应该只表示当前快照。
- `bucket/objectKey/uploadId/versionNo/verifyStatus` 可以优先写入 `resource.extra`。
- 历史版本治理信息通过新增 `resource_version` 表独立保存即可。

例如当前快照的 `extra_json` 可写成：

```json
{
  "profile": "resource-file",
  "filename": "a.csv",
  "mime": "text/csv",
  "bucket": "dris-repo-prod-1330585503",
  "objectKey": "identifiers/xxx/resource/up-10",
  "uploadId": "up-10",
  "_versionNo": 3,
  "_sourceUploadId": "up-10",
  "_verifyStatus": "VERIFIED",
  "_bindMode": "upload"
}
```

因此，最小侵入方案中，`resource` 不做表结构修改。

## 6. 新增数据对象设计

## 6.1 新增 `resource_version` 表

本次只新增一张表，用于保存历史版本事实。

建议建表：

```sql
CREATE TABLE IF NOT EXISTS resource_version (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    identifier VARCHAR(30) NOT NULL,
    version_no BIGINT NOT NULL,
    component_type VARCHAR(32) NOT NULL,
    role VARCHAR(32) NOT NULL DEFAULT 'primary',
    storage_type VARCHAR(64) NOT NULL,
    access_method VARCHAR(64) NOT NULL,
    content_type VARCHAR(128) NOT NULL,
    format VARCHAR(128) NOT NULL,
    locator TEXT NOT NULL,
    size_bytes BIGINT NOT NULL DEFAULT 0,
    hash_value VARCHAR(255) DEFAULT '',
    etag VARCHAR(255) DEFAULT '',
    provider_version_id VARCHAR(255) DEFAULT '',
    source_upload_id VARCHAR(64) DEFAULT '',
    bind_mode VARCHAR(32) NOT NULL DEFAULT 'direct',
    verify_status VARCHAR(32) NOT NULL DEFAULT '',
    created_at VARCHAR(64) NOT NULL,
    extra_json TEXT,
    UNIQUE KEY uk_resource_version_identifier_no (identifier, version_no),
    KEY idx_resource_version_identifier_time (identifier, created_at),
    CONSTRAINT fk_resource_version_identifier FOREIGN KEY (identifier) REFERENCES identifier_metadata(identifier) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

说明：

- 不再把版本信息加到旧表。
- 所有历史版本都进入这张表。
- 当前 `resource` 仍只保留最新快照。

## 6.2 为什么只新增一张表就够

因为本次真正新增的业务能力只有一个核心事实：

“同一个标识的组件有历史版本序列。”

这类历史事实最适合用独立表保存，而不是反复扩展当前状态表。

## 7. 两条绑定路径设计

## 7.1 上传型绑定

适用场景：

- `resource` 文件由本系统对象存储托管
- `tool` 为可下载工具包，且也由本系统对象存储托管

流程：

1. 创建上传会话
2. 客户端上传对象到对象存储
3. 调用 `completeUpload`
4. 后端执行实体存在校验
5. 校验通过后写入 `resource_version`
6. 更新 `resource` 当前快照

特点：

- 需要 `bucket/object_key`
- 需要实体校验
- 适合真实文件资源共享

## 7.2 直连型绑定

适用场景：

- `service`
- `tool(local_exec)`
- 已经有外部 URI 的 `resource`
- 已经有外部 URI 的 `tool`

流程：

1. 调用 `PUT /api/v2/identifiers/{identifier}/component`
2. 后端校验组件语义合法性
3. 直接写入 `resource_version`
4. 更新 `resource` 当前快照

特点：

- 不依赖上传会话
- 不依赖对象存储
- 更符合 `service` 和本地工具的实际语义

## 7.3 组件绑定矩阵

| 组件类型 | 典型场景 | 是否需要 upload_session | 绑定方式 |
|---|---|---|---|
| `resource` | 平台托管文件 | 是 | 上传型绑定 |
| `resource` | 外部下载地址 | 否 | 直连型绑定 |
| `tool` | 工具包文件 | 可选 | 上传型或直连型 |
| `tool` | `local_exec` 本地工具 | 否 | 直连型绑定 |
| `service` | API 服务入口 | 否 | 直连型绑定 |

## 8. 上传完成校验设计

## 8.1 校验目标

对于上传型绑定，`completeUpload` 必须保证：

1. 对象真实存在
2. 对象大小正确
3. 若声明了 `sha256`，则摘要一致

## 8.2 校验输入来源

直接复用 `upload_session` 现有字段：

- `bucket`
- `object_key`
- `expected_size`
- `expected_sha256`

无需为此改表。

## 8.3 校验结果保存策略

校验结果保存到 `upload_session.extra_json` 中，例如：

- `_verifyStatus`
- `_verifyMessage`
- `_actualSize`
- `_actualHash`
- `_completedAt`
- `_etag`

这样无需改表结构，也能保留完整排障信息。

## 8.4 `completeUpload` 新流程

建议流程如下：

1. 读取 `upload_session`
2. 校验 session 状态和过期时间
3. 调用对象存储探测能力，检查对象是否存在
4. 校验实际大小与 `expected_size`
5. 如果传入了 `expected_sha256`，校验摘要
6. 构造 `Resource`
7. 分配新版本号
8. 插入 `resource_version`
9. 更新 `resource` 当前快照
10. 将校验结果写回 `upload_session.extra_json`
11. 更新 `upload_session.status = done`

## 8.5 建议失败码

- `OBJECT_NOT_FOUND`
- `OBJECT_SIZE_MISMATCH`
- `OBJECT_HASH_MISMATCH`
- `OBJECT_VERIFY_FAILED`

## 9. 资源版本治理设计

## 9.1 版本号分配规则

版本号不在创建上传会话时分配，而在真正绑定成功时分配：

- 若该标识从未产生版本，则 `versionNo = 1`
- 否则 `versionNo = max(version_no) + 1`

这样可以避免多个并发上传会话抢同一个版本号。

## 9.2 当前快照的存储方式

当前快照仍存入 `resource` 表。

新增的版本治理信息放入 `resource.extra_json`，如：

- `_versionNo`
- `_sourceUploadId`
- `_verifyStatus`
- `_bindMode`
- `bucket`
- `objectKey`

这样不需要修改 `resource` 表结构。

## 9.3 历史版本的存储方式

每次绑定成功后，都插入一条 `resource_version`：

- 上传型绑定：`bind_mode = upload`
- 直连型绑定：`bind_mode = direct`

无论是上传型还是直连型，都能形成统一版本历史。

## 9.4 旧数据兼容策略

最小侵入方案不强制回填旧数据。

兼容策略如下：

1. 旧的 `resource` 行继续可用。
2. 若某标识尚无 `resource_version` 历史，则版本历史接口可返回空列表。
3. 从新逻辑上线之后，新的绑定操作开始进入 `resource_version`。
4. 如需增强论文展示效果，可额外提供一个离线回填脚本，把当前 `resource` 快照回填为 `versionNo=1` 的历史记录，但这不是系统上线必需项。

## 10. `objectKey` 设计调整

## 10.1 当前问题

当前 `objectKey` 固定，会导致重复上传覆盖。

## 10.2 新设计

建议改为：

- `identifiers/{identifier}/resource/{uploadId}`
- `identifiers/{identifier}/tool/{uploadId}`

说明：

- `service` 默认不再走上传型绑定，因此不再生成 `service/{uploadId}` 上传路径。
- 使用 `uploadId` 作为对象路径后缀，可在不引入额外表字段的情况下天然避免覆盖。

## 11. 三类组件语义设计

## 11.1 `resource`

语义：真实共享数据实体。

特点：

- 可以是平台托管对象
- 也可以是外部下载地址
- 允许下载
- 允许跨节点解析后共享

推荐约束：

- `storageType = external_uri`
- `accessMethod = download`

## 11.2 `tool`

语义：共享处理能力。

可能有两类：

1. 工具包文件
   - 可上传到对象存储
   - 可下载
2. 本地执行工具
   - `storageType = local_exec`
   - 不下载，只执行

因此，`tool` 不应被一刀切地要求必须创建上传会话。

## 11.3 `service`

语义：共享服务接口。

特点：

- 主体是 API 调用入口
- 核心是“调用”，不是“下载”
- 应直接绑定服务地址，而不是走文件上传流程

推荐约束：

- `storageType = api_service`
- `accessMethod = api_call`
- `locator` 为 HTTP/HTTPS 地址

## 12. 接口改造设计

## 12.1 保持不变的接口

保留：

- `POST /api/v2/identifiers/{identifier}/upload-sessions`
- `POST /api/v2/upload-sessions/{uploadId}/complete`
- `PUT /api/v2/identifiers/{identifier}/component`
- `GET /api/v2/identifiers/{identifier}/component`
- `POST /api/v2/downloads/presign`

## 12.2 行为调整

### 12.2.1 `createUploadSession`

行为调整为：

- 支持：`resource`
- 支持：可下载包型 `tool`
- 不支持：`service`
- 不支持：`tool(local_exec)`

对于 `service`，应直接返回校验错误，提示改用 `PUT /component` 直绑。

### 12.2.2 `completeUpload`

行为调整为：

- 必须先做实体存在校验
- 校验通过后才允许绑定
- 绑定成功后写入 `resource_version`
- 当前快照更新到 `resource`

### 12.2.3 `upsertComponent`

新增行为：

- 不再只是“覆盖当前组件”
- 每次合法绑定都应写一条 `resource_version`
- 对于 `service` 和 `tool(local_exec)`，这是主绑定路径

### 12.2.4 `downloadPresign`

建议按组件语义区分：

- `resource`
  - 若是对象存储托管资源，返回下载地址
  - 若是外部 HTTP/HTTPS 地址，可直接返回原始 `locator`
- `tool`
  - 若 `storageType = external_uri`，允许下载
  - 若 `storageType = local_exec`，返回不支持
- `service`
  - 默认返回不支持

## 12.3 新增版本查询接口

建议新增：

1. `GET /api/v2/identifiers/{identifier}/component/versions?page=1&size=10`
2. `GET /api/v2/identifiers/{identifier}/component/versions/{versionNo}`

这两个接口只依赖新表 `resource_version`，不要求旧表变更。

## 13. 代码修改点

## 13.1 `dris-java-sdk`

### `CreateUploadSessionHandler`

修改点：

1. 限制 `service` 不再创建上传会话。
2. 限制 `tool(local_exec)` 不再创建上传会话。
3. `objectKey` 改为带 `uploadId` 的唯一路径。

### `CompleteUploadHandler`

修改点：

1. 增加对象存储实体校验。
2. 校验结果写回 `upload_session.extra`。
3. 分配版本号。
4. 插入 `resource_version`。
5. 更新 `resource` 当前快照，并把版本治理信息写入 `resource.extra`。

### `UpsertComponentHandler`

修改点：

1. 保留现有直接绑定逻辑。
2. 每次绑定成功后新增一条 `resource_version`。
3. 将 `_versionNo`、`_bindMode` 等写入 `resource.extra`。

### `CreateDownloadPresignHandler`

修改点：

1. `service` 直接拒绝下载。
2. `tool(local_exec)` 直接拒绝下载。
3. 若 `resource/tool` 为外部 HTTP/HTTPS 地址，可直接返回 `locator`。
4. 若为对象存储托管对象，则继续根据 `objectKey` 返回下载地址。

### JDBC Repository 层

修改点：

1. `JdbcUploadSessionRepository` 不改表结构，只保留 `extra_json` 回写能力。
2. `JdbcDigitalObjectRepository` 保持 `resource` 原有读写 SQL 不变。
3. 新增 `resource_version` 的插入和查询能力。

## 13.2 `dris-enterprise-backend-v2`

### `IdentifierResourceService`

修改点：

1. 保留现有 `upsertComponent` 服务逻辑。
2. 增加组件版本查询服务封装。

### `IdentifierResourceController`

修改点：

1. 保留现有组件获取和组件直绑接口。
2. 新增版本历史分页查询接口。

## 14. 数据库存储策略总结

## 14.1 不修改的表

以下表保持结构不变：

- `upload_session`
- `resource`
- `identifier_metadata`

## 14.2 新增的表

只新增：

- `resource_version`

## 14.3 扩展信息放哪里

### 上传校验扩展信息

放入 `upload_session.extra_json`：

- `_verifyStatus`
- `_verifyMessage`
- `_actualSize`
- `_actualHash`
- `_completedAt`

### 当前资源治理扩展信息

放入 `resource.extra_json`：

- `bucket`
- `objectKey`
- `uploadId`
- `_versionNo`
- `_sourceUploadId`
- `_verifyStatus`
- `_bindMode`

### 历史版本信息

放入 `resource_version`

## 15. 事务与一致性设计

对于上传型绑定，建议在同一个事务中完成：

1. 插入 `resource_version`
2. 更新 `resource`
3. 更新 `upload_session.status`
4. 更新 `upload_session.extra_json`

这样可以避免：

- 历史表已写，但当前快照未更新
- 当前快照已更新，但 session 仍停留在 `committing`

对于直连型绑定，建议在同一个事务中完成：

1. 插入 `resource_version`
2. 更新 `resource`

## 16. 测试方案

## 16.1 单元测试

1. `resource` 创建上传会话成功
2. `service` 创建上传会话失败
3. `tool(local_exec)` 创建上传会话失败
4. `completeUpload` 对象不存在时失败
5. `completeUpload` 大小不一致时失败
6. `completeUpload` 摘要不一致时失败
7. 上传成功后 `resource_version` 增加一条记录
8. 直连绑定成功后 `resource_version` 增加一条记录
9. `downloadPresign` 对 `service` 返回不支持
10. `downloadPresign` 对 `tool(local_exec)` 返回不支持

## 16.2 集成测试

1. 同一标识两次上传，版本历史应出现两条记录
2. 当前 `resource.extra._versionNo` 应指向最新版本
3. 直连绑定 `service` 后，组件可解析但不可下载
4. 外部 URI 型 `resource` 直绑后，可返回外部下载地址

## 17. 分阶段实施建议

## 第一阶段：最小可行改造

实施内容：

1. `service` 从上传会话路径中移除
2. `tool(local_exec)` 从上传会话路径中移除
3. `objectKey` 改为带 `uploadId` 的唯一路径
4. `completeUpload` 增加实体存在校验
5. 新增 `resource_version` 表
6. 版本治理信息写入 `resource.extra`
7. 上传校验信息写入 `upload_session.extra`

这一阶段已经能满足：

- 共享资源真实性增强
- 资源版本可追踪
- 数据库旧表基本不动

## 第二阶段：可选增强

实施内容：

1. 对象存储接入抽象化
2. 真正接入 COS SDK 生成签名 URL
3. 版本历史查询分页接口完善
4. 回填旧数据为历史版本

这一阶段是增强项，不是最小上线必需项。

## 18. 对毕设表述的价值

采用本方案后，可以在论文中表述为：

“系统在保持原有数据库主结构基本不变的前提下，通过引入上传实体校验机制、资源版本历史表以及组件双路径绑定模型，实现了数字对象共享资源的真实性保障、版本可追溯治理以及文件资源、工具能力、服务接口三类共享对象的统一管理。”

这个表述有三个优点：

1. 强调你不是简单上传文件，而是在做共享治理。
2. 强调你考虑了系统演进成本，没有粗暴推翻现有数据结构。
3. 强调 `resource / tool / service` 的统一建模能力。

## 19. 最终结论

如果目标是“尽量降低原先数据库表的修改”，那么最合适的方案是：

1. 不改 `upload_session` 表结构。
2. 不改 `resource` 表结构。
3. 只新增一张 `resource_version` 表。
4. 版本号、上传来源、校验结果等扩展字段全部先写入 `extra_json`。
5. `service` 和 `tool(local_exec)` 改走直连型绑定，不再创建上传会话。
6. `resource` 和可下载包型 `tool` 继续使用上传型绑定，并在 `completeUpload` 中做实体校验。

这套方案在功能、改造量、兼容性之间比较平衡，适合作为你当前系统的中等改造版本和毕设实现方案。
