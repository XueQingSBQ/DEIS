# 跨节点批量解析双模式设计报告（递归与迭代对比版）

## 摘要

针对 `dris-enterprise-backend-v2` 目前仅支持单条跨节点解析和本地批量解析的现状，本文提出一种面向层级治理网络的跨节点批量解析双模式方案。该方案同时保留两条实现路线：其一为“按下一跳分组的递归批量转发模式”，其二为“入口节点集中调度的迭代批量解析模式”。两种模式共享同一套标识归属规则、路由表、DRIRP 安全机制与审计能力，但在请求控制权、链路组织方式、节点负载分布和实验观察粒度上存在明显差异。

从方法来源上看，本文方案借鉴了 DNS 的递归/迭代解析控制模型、Handle System 的前缀归属思想、Chord 的分布式查找对照思路，以及分布式查询处理中的站点级分组优化思想。在此基础上，结合 DRIS 的“区域编码 + 组织编码”层级语义，提出适合毕业设计实现与实验对比的双模式批量解析架构。本文不主张只实现单一方案，而是像现有单条跨节点解析一样，同时保留递归和迭代两种路径，以便在论文中做设计与性能上的系统性比较。

## 1. 研究背景与问题提出

### 1.1 系统背景

当前系统已经具备以下基础能力：

- 单条标识本地解析
- 单条标识跨节点分布式解析
- 节点注册、父子关系维护与路由传播
- DRIRP 消息鉴权、防重放与跨节点审计
- 本地批量元数据解析接口 `POST /api/v2/identifiers/resolve/batch`

但当前“批量解析”仍然局限于本地节点，主要表现为：

- 无法跨节点批量聚合解析远程 identifier
- 无法表达单项超时、路由缺失、上游失败等细粒度状态
- 多个远程 identifier 会退化为逐条单次解析，网络开销和路由开销被放大
- 不能像单条解析那样，在系统层面比较递归与迭代两种控制方式

### 1.2 研究问题

本文关注的问题可以描述为：

> 在 DRIS 多层级节点网络中，如何设计一种同时支持递归和迭代两种控制模式的跨节点批量解析机制，使其既能保持层级治理语义，又能降低批量请求的网络通信开销，并满足毕业设计中的对比实验要求？

该问题兼具以下特征：

- 是分布式定位与获取问题
- 是批量请求的组织与调度问题
- 是层级治理网络中的工程实现问题
- 是需要做对照实验的算法与系统设计问题

## 2. 需求分析

### 2.1 功能需求

系统需要满足以下功能需求：

1. 支持一次请求解析多个 identifier
2. 支持本地与远程混合场景
3. 支持每个 identifier 独立返回状态
4. 支持输入顺序保持与重复项回填
5. 支持递归与迭代两种批量解析模式
6. 支持链路跟踪、跳数控制、超时控制与环路检测

### 2.2 非功能需求

系统还需要满足：

- 高性能：尽量减少跨节点消息数量
- 低耦合：复用现有路由和 DRIRP 基础设施
- 可扩展：后续可扩展到 `DIGITAL_OBJECT` 与 `RESOURCE`
- 可观测：可输出 trace、跳数、节点统计和失败原因
- 安全性：复用现有跨节点消息鉴权机制
- 可实验：支持与单条逐个解析方案、广播方案进行对比

## 3. 相关工作与方法来源

### 3.1 DNS 的递归与迭代解析思想

DNS 在 RFC 1034 中定义了递归解析和迭代解析两种控制方式：

- 递归模式下，请求会沿着名字服务链条逐级推进，客户端只等待最终结果
- 迭代模式下，当前服务返回 referral，客户端或入口端继续请求下一跳

这对本文启发很直接：

- 递归批量解析可以由中间节点继续完成后续子批次转发
- 迭代批量解析可以由入口节点统一调度全部后续批次

因此，DNS 提供的是“控制模式设计模板”。

### 3.2 Handle System 的前缀归属思想

Handle System 在 RFC 3650、RFC 3651 中强调：

- 句柄前缀决定归属服务域
- 上层可完成服务定位与转介
- 下层句柄服务负责本地实际解析

这与 DRIS 的 `regionCode + orgCode` 前缀归属模型非常接近。Handle System 提供的是“标识归属与服务转介模板”。

### 3.3 Chord 的分布式查找思想

Chord 通过一致性哈希实现去中心化定位，具有良好的扩展性和 `O(logN)` 查找复杂度，但它的问题在于：

- 它会打破行政层级和组织归属语义
- 不利于你当前“国家-省-市-县”结构的论文表达
- 不适合作为主实现，但非常适合作为理论对照

因此，Chord 更适合用来说明：本文为什么不采用完全去中心化哈希路由。

### 3.4 分布式查询处理中的批量分组思想

分布式查询处理中，一类经典优化思路是“先按站点分组，再并发发送”，而不是逐条远程访问。其核心启发在于：

- 跨站点通信本身就是主要成本
- 面对批量数据项时，应该优先减少消息数而不是只关注单次计算开销
- 相同目标站点的数据项应该尽量合并发送

这一思想是本文批量解析方案的主要性能优化来源。

## 4. 设计目标

### 4.1 总体目标

本文方案的总体目标是：

- 在 DRIS 层级治理网络中，构建一套可同时支持递归与迭代两种控制模式的跨节点批量解析框架
- 通过统一的请求模型、统一的路由归属规则和统一的返回结构，对两种模式进行公平比较

### 4.2 具体目标

1. 保留现有单条解析模式不变
2. 保留现有本地批量接口不变
3. 新增跨节点批量解析接口
4. 提供 `RECURSIVE` 与 `ITERATIVE` 两种批量模式
5. 支持部分成功返回与逐项错误码
6. 提供适合毕设实验的统计信息与对照基线

## 5. 双模式总体设计

### 5.1 模式定义

本文不在 `B` 和 `C` 中二选一，而是将它们都设计为正式支持的运行模式：

- 方案 B：`RECURSIVE_BATCH`
- 方案 C：`ITERATIVE_BATCH`

与现有单条解析类似：

- 递归模式强调“中间节点继续处理”
- 迭代模式强调“入口节点集中控制”

### 5.2 模式映射关系

| 模式 | 控制者 | 中间节点职责 | 入口节点压力 | 网络往返特点 | 适合场景 |
| --- | --- | --- | --- | --- | --- |
| `RECURSIVE_BATCH` | 当前处理节点 | 本地解析 + 再分组 + 继续下发 | 中 | 中间节点承担更多转发 | 更贴近现有单条递归实现 |
| `ITERATIVE_BATCH` | 入口节点 | 仅返回局部结果或下一跳建议 | 高 | 入口节点往返更多 | 更适合实验观测与统一调度 |

## 6. 方案 A、B、C 的定位关系

为便于论文写作，建议把三种方案统一描述为：

### 6.1 方案 A：逐条单次分布式解析基线

- 不是真正的批量协议
- 只是把多个 identifier 逐条调用现有单条 `resolveDistributed`
- 作为工程基线与实验基线

### 6.2 方案 B：递归式跨节点批量解析

- 入口节点先按下一跳分组
- 每组形成一个子批次
- 中间节点收到后继续做本地处理和二次分组
- 请求沿层级拓扑递归推进
- 最终由目标节点完成本地批量解析

### 6.3 方案 C：迭代式跨节点批量解析

- 入口节点维护待处理队列或批次队列
- 中间节点只返回“局部结果”或“下一跳建议”
- 入口节点根据返回结果继续发起下一跳请求
- 最终由入口节点统一聚合全链路结果

### 7.1 逻辑组件

### 7.2 组件职责

| 组件 | 职责 |
| --- | --- |
| `IdentifierBatchResolveController` | 暴露跨节点批量解析接口 |
| `IdentifierBatchResolveService` | 负责请求校验、traceId、策略分发 |

- 路由规则统一，不因模式不同而改变归属判断
- 返回结构统一，避免实验结果无法横向比较
- 仅控制流程不同，业务语义保持一致

## 8. 接口设计

### 8.1 REST 接口

建议保留旧接口，并新增跨节点双模式接口：

- 旧接口：`POST /api/v2/identifiers/resolve/batch`
- 新接口：`POST /api/v2/identifiers/resolve/batch/distributed`

### 8.2 请求对象

建议新增 `BatchResolveRequest`：

```json
{
  "identifiers": [
    "1100ABCD019320260101AAAAAAAAAA",
    "3701WXYZ019320260101BBBBBBBBBB"
  ],
  "resolveType": "METADATA",
  "strategy": "RECURSIVE",
  "timeoutMs": 8000,
  "ttl": 8,
  "maxParallelNodes": 8,
```

关键字段说明：

- `maxParallelNodes`：控制扇出并发度

- `traceId`
- `strategy`
- `partial`
- `total`
- `successCount`
- `failureCount`
- `elapsedMs`
- `items[]`
- `nodeStats[]`

这样无论递归还是迭代，客户端都能用同一结构接收结果，便于实验统计。

## 10. 递归批量解析设计（方案 B）

### 10.1 核心思想

递归模式下，入口节点只负责首次分组和第一次扇出。后续如果某个中间节点发现自己不是最终目标节点，则继续执行同样的“本地解析 + 二次分组 + 继续下发”逻辑。

### 10.2 处理流程

1. 入口节点接收批量请求
2. 提取每个 identifier 的 `targetCode`
3. 本地项直接本地批量解析
4. 远程项按下一跳节点分组
5. 形成多个子批次并并发发送 `RESOLVE_BATCH_FORWARD`
6. 中间节点收到后重复 2-5 步
7. 目标节点完成本地批量解析并返回结果
8. 父节点逐层聚合返回值，直到回到入口节点

### 10.3 特点分析

优点：

- 与现有单条递归解析实现风格一致
- 入口节点状态较轻
- 中间节点可以分担调度与分桶压力

缺点：

- 中间节点需要承担更多逻辑
- 链路控制分散，实验观测需要更强日志支持

## 11. 迭代批量解析设计（方案 C）

### 11.1 核心思想

迭代模式下，入口节点是唯一调度中心。中间节点不继续递归下发，而是将“下一跳建议”或“子节点列表”返回给入口节点，由入口节点决定下一轮请求如何发起。

### 11.2 处理流程

1. 入口节点接收批量请求
2. 按路由规则生成初始待处理队列
3. 并发发送第一轮批量请求
4. 中间节点返回局部结果和下一跳建议
5. 入口节点更新待处理队列
6. 入口节点继续向后续节点发起下一轮请求
7. 直到全部完成或超时
8. 入口节点统一输出最终聚合结果

### 11.3 特点分析

优点：

- 所有控制都集中在入口节点
- 更便于统计总跳数、总轮次、总消息数
- 更适合毕业设计实验中的可视化分析

缺点：

- 入口节点压力更高
- 请求轮次可能更多
- 状态管理更复杂

## 12. 双模式统一算法框架

### 12.1 统一步骤

无论递归还是迭代，以下步骤都保持一致：

1. 参数校验
2. identifier 去重
3. 提取 `targetCode`
4. 本地与远程项分离
5. 下一跳计算
6. 结果聚合与顺序恢复
7. 错误回填与统计生成

### 12.2 差异点

两种模式的差异主要集中在：

- 谁继续发起下一跳请求
- 中间节点是否承担再分组逻辑
- 节点统计由谁汇总
- 请求状态由谁持有

## 13. 伪代码设计

### 13.1 递归模式伪代码

```text
+function recursiveBatchResolve(batch):
+    localItems, remoteBuckets = plan(batch)
+    localResults = resolveLocal(localItems)
+    remoteResults = []
+    for each bucket in remoteBuckets parallel:
+        remoteResults += sendBatch(bucket.nextHop, bucket.items, strategy=RECURSIVE)
+    return merge(localResults, remoteResults)
```

### 13.2 迭代模式伪代码

```text
+function iterativeBatchResolve(batch):
+    queue = buildInitialQueue(batch)
+    finalResults = []
+    while queue not empty:
+        currentRound = takeRound(queue)
+        responses = parallelSend(currentRound, strategy=ITERATIVE)
+        finalResults += collectLocalResults(responses)
+        queue += extractNextHopTasks(responses)
+    return merge(finalResults)
```

## 14. 复杂度与性能预期

### 14.1 方案 A

- 计算复杂度：`O(N)`
- 网络消息数：接近 `O(N * H)`
- 特征：简单但开销最大

### 14.2 方案 B

- 计算复杂度：`O(N)`
- 网络消息数：接近 `O(G * H)`，其中 `G` 为分组后的节点桶数
- 特征：对通信优化最直接，入口压力适中

### 14.3 方案 C

- 计算复杂度：`O(N)`
- 网络消息数：仍低于逐条方式，但入口节点往返轮次更明显
- 特征：实验统计最好做，但入口压力更高

## 15. 容错与安全设计

### 15.1 容错设计

双模式都必须支持：

- `ROUTE_NOT_FOUND`
- `TTL_EXCEEDED`
- `DEADLINE_EXCEEDED`
- `LOOP_DETECTED`
- `UPSTREAM_ERROR`
- `PARTIAL_SUCCESS`

### 15.2 安全设计

双模式统一复用：

- DRIRP 消息签名
- 防重放
- 时间窗校验
- 跨节点审计

即：模式变化只改变控制流程，不改变安全模型。

## 17. 实验设计与论文对照基线

### 17.1 对照基线

建议论文中至少设置三组对照：

- Baseline A：逐条单次分布式解析
- Proposed B：递归式跨节点批量解析
- Proposed C：迭代式跨节点批量解析

### 17.2 比较指标

建议统计：

- 平均延迟
- P95 延迟
- 网络消息数
- 跨节点请求次数
- 节点 CPU 占用
- 入口节点线程池占用
- 成功率与部分成功率
- 节点故障下的退化行为

### 17.3 预期结论

理论上预期：

- `B/C` 都优于 `A`
- `B` 在吞吐和通信开销上通常更优
- `C` 在可观测性和实验控制上更优
- `B` 更适合作为生产默认模式
- `C` 更适合作为毕设实验模式和分析模式

## 18. 创新点提炼

从毕业设计角度，建议把创新点写成以下 4 点：

1. 在 DRIS 层级治理网络中提出跨节点批量解析双模式框架
2. 将单条解析中的递归/迭代思想扩展到批量解析场景
3. 提出“按下一跳分组”的批量转发机制，降低通信放大效应
4. 给出可直接实验对比的统一协议与统一返回结构

## 20. 结论

针对你的毕业设计目标，最合理的路线不是在方案 B 和方案 C 中二选一，而是像当前单条跨节点解析一样，把两种模式都做出来：

- `B` 作为递归批量解析正式方案
- `C` 作为迭代批量解析正式方案

这样做的价值有三层：

- 工程上，你能得到一套更完整、更可演进的跨节点批量解析系统
- 论文上，你能形成“设计方案 + 方法对比 + 实验验证”的完整闭环
- 答辩上，你不仅能说明“系统能跑”，还能说明“为什么这样设计、和其他方法相比有什么优势”
