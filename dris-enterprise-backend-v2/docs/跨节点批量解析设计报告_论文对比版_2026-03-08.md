# 跨节点批量解析设计报告（论文对比版）

## 摘要

针对 `dris-enterprise-backend-v2` 当前仅支持“单条跨节点解析”和“本地批量解析”的现状，本文提出一种面向多层级节点网络的跨节点批量解析方案。该方案以“按下一跳节点分组 + 递归批量转发 + 结果聚合回填”为核心思想，在不改变现有标识编码规则、不引入额外核心业务表的前提下，实现多标识的一次性跨节点解析。与将每个标识逐条执行单次分布式解析的方式相比，所提方案显著减少节点间消息数量和重复路由计算次数，并支持部分成功返回、顺序保持、环路检测、超时控制和链路审计。

从研究方法上看，本文方案综合借鉴了四类代表性思路：一是 DNS 的分层递归/迭代解析机制；二是 Handle System 的前缀归属与服务转介思想；三是 Chord 分布式哈希表中的去中心化查找思想；四是分布式查询处理中以通信代价最小化为目标的并行分发思想。本文在上述方法基础上，结合 DRIS 的“区域编码 + 组织编码”层级语义，提出一种更适合行政分层节点体系的工程化批量解析设计。

## 1. 研究背景与问题定义

### 1.1 系统背景

当前系统已经具备如下能力：

- 单条标识本地解析
- 单条标识跨节点分布式解析
- 节点注册与父子拓扑维护
- 路由传播与下一跳定位
- DRIRP 消息鉴权、防重放与跨节点审计

但现有系统在“批量解析”方面仍存在明显不足：

- `POST /api/v2/identifiers/resolve/batch` 只能调用本地 `resolveIdentifierBatch`
- 对远程标识缺少批量跨节点解析能力
- 返回结构过于简单，不能表达单项超时、路由缺失、上游失败等状态
- 多个远程标识会退化为逐条单次解析，导致网络开销放大

### 1.2 研究问题

本文关注的问题是：

> 在一个由国家、省、市、县等多层级节点组成的 DRIS 网络中，如何设计一种既保持层级管理语义、又能高效执行跨节点批量标识解析的机制？

该问题本质上兼具以下三个特征：

- 它是一个“分布式定位与获取”问题
- 它是一个“多请求合并与调度”问题
- 它还是一个“分层治理网络中的工程实现”问题

因此，不能简单使用单条解析循环，也不能直接套用完全去中心化的 DHT 方案。

## 2. 需求分析

### 2.1 功能需求

系统需要满足以下功能需求：

1. 一次请求能够解析多个 identifier
2. 请求中的标识可分布在不同节点甚至不同分支
3. 返回结果能够逐项表示成功或失败
4. 输出结果应与输入顺序保持一致
5. 对于本地可处理项，应优先在本地完成
6. 对于远程项，应尽量减少重复跨节点通信

### 2.2 非功能需求

系统还应满足以下非功能需求：

- 高性能：避免逐条远程调用带来的高放大开销
- 低耦合：尽量复用现有 `DrirpResolutionService` 与路由表能力
- 可扩展：后续可扩展到 `DIGITAL_OBJECT` 与 `RESOURCE`
- 可观测：支持 traceId、耗时、失败原因与节点统计
- 安全性：复用现有 DRIRP 鉴权和防重放机制
- 可实验：能够与其他典型方法进行理论或实验比较

## 3. 相关工作与方法对比

本节选取 4 类与本文最相关的方法作为比较对象。

### 3.1 DNS 分层解析方法

DNS 的经典设计由 RFC 1034 给出。其核心思想是：

- 名称空间按层级组织
- 解析可采用 recursive 或 iterative 两种模式
- 上级服务通过 referral 把查询引导到更合适的下级服务

这与 DRIS 中“前缀决定归属节点、上层知道下层大致方向”的结构非常接近。

可借鉴点：

- 递归/迭代双模式思路
- 基于层级前缀的路由转介
- TTL 与循环保护机制

局限性：

- DNS 主要面向单个域名解析，不强调批量分组优化
- DNS 的结果大多是轻量名称记录，不直接面对复杂元数据对象
- DNS 并不直接处理“批量请求的部分成功返回”问题

因此，DNS 更适合作为“跨节点单条解析控制模型”的参考，而不是批量优化模型的完整答案。

### 3.2 Handle System 持久标识解析方法

Handle System 的官方规范见 RFC 3650、RFC 3651、RFC 3652。其关键思想包括：

- 标识由前缀和后缀构成
- 前缀决定由哪个服务域负责管理
- 系统使用 Global Handle Registry 与 Local Handle Service 协同完成解析
- 当本地服务不直接持有目标句柄时，可通过服务信息转介到其他句柄服务

这与 DRIS 的 `regionCode + orgCode + object-part` 结构高度相似。Handle System 更接近“持久标识解析”的应用语境，因此比 DNS 更贴近你的系统。

可借鉴点：

- “前缀归属”而非“哈希归属”
- 上层知道责任域，下层负责本地解析
- 通过服务转介实现跨站点解析
- 在协议层支持服务发现与结果封装

局限性：

- Handle System 更关注单个句柄的解析正确性
- 对批量请求的分组调度与性能优化讨论较少
- 其全球注册表模式更偏强中心引导，不完全适合你现在的多层自治节点实验结构

因此，Handle System 可作为“标识解析语义与路由归属模型”的直接参考。

### 3.3 Chord 分布式哈希查找方法

Stoica 等人在 Chord 中提出了一种基于一致性哈希和 `O(log N)` 查找复杂度的分布式定位方法。其核心特点是：

- 节点组织为逻辑环
- 标识通过哈希映射到逻辑空间
- 每个节点维护少量路由信息（finger table）
- 查找过程不依赖固定层级结构

可借鉴点：

- 查找复杂度低
- 去中心化程度高
- 大规模节点加入和退出时具备较好的扩展性

局限性：

- 哈希映射会打破 `regionCode + orgCode` 的管理语义
- 不适合需要保持行政分层、组织归属、父子管控关系的场景
- 不利于论文中展示“国家-省-市-县”层级治理网络的业务含义

因此，Chord 更适合作为理论上的“去中心化对照方法”，而不适合作为你的主实现路线。

### 3.4 分布式查询优化中的并行分发方法

Shyu 在 “A One-Shot Semi-Join Method for Distributed Query Processing” 中讨论了如何通过并行发送投影与连接约束，降低分布式查询的响应时间和通信开销。虽然该方法面对的是关系数据库查询，而不是标识解析，但它提供了一个对本文非常有价值的启发：

- 与其把请求拆成大量独立远程调用，不如先进行分组与压缩，再按站点并行发送
- 减少跨站点通信次数本身就是核心优化目标
- 响应时间优化不仅依赖计算，还依赖“网络发送组织方式”

可借鉴点：

- 分组与并行下发
- 尽量减少跨节点通信次数
- 从“数据项逐条处理”转向“按站点组织处理”

局限性：

- 其处理对象是分布式关系查询，不是层级标识解析
- 不涉及层级路由、转介与多跳递归问题
- 不处理部分成功返回和路径追踪

因此，这类方法更适合作为“批量优化思想来源”，而非完整协议设计来源。

## 4. 文献方法与本文方案的对比分析

### 4.1 对比维度

本文选取以下 8 个维度进行比较：

- 拓扑组织方式
- 路由依据
- 是否支持层级治理语义
- 是否天然支持批量请求
- 节点间通信成本
- 是否适合部分成功返回
- 是否便于工程实现
- 是否适合作为毕业设计实验对象

### 4.2 方法对比表

| 方法 | 拓扑方式 | 路由依据 | 批量支持 | 层级治理语义 | 通信开销优化 | 适合 DRIS 程度 |
| --- | --- | --- | --- | --- | --- | --- |
| DNS 递归/迭代解析 | 严格层级 | 域名前缀与委派关系 | 弱 | 强 | 中 | 高 |
| Handle System | 前缀归属 + 服务转介 | 前缀与句柄服务 | 弱 | 强 | 中 | 很高 |
| Chord | 逻辑环 | 一致性哈希 | 中 | 弱 | 高 | 低 |
| One-shot Semi-Join | 多站点并行查询 | 查询分解与站点分发 | 强 | 弱 | 很高 | 中 |
| 本文方案 | 层级拓扑 + 批量分桶 | 前缀归属 + 下一跳路由 | 很强 | 很强 | 很高 | 很高 |

### 4.3 对比结论

综合比较后，可以得到如下结论：

1. 从“标识解析语义”角度看，Handle System 最接近你的系统
2. 从“层级解析控制方式”角度看，DNS 的 recursive/iterative 思路最接近你现有实现
3. 从“去中心化可扩展性”角度看，Chord 很强，但不符合你的层级治理要求
4. 从“批量通信优化”角度看，分布式查询处理的分组并行思想最值得借鉴

因此，最合理的路线不是机械复现某一个经典方法，而是结合业务场景做“方法融合”：

- 用 DNS/Handle 解决“怎么跨层级找对节点”
- 用分布式查询优化思想解决“怎么批量减少通信开销”
- 不采用 Chord 的哈希路由，但用它作为理论对照说明层级路由的合理性

## 5. 本文方案的设计思想

### 5.1 基本思想

本文方案采用如下设计思想：

- 以 `regionCode + orgCode` 作为目标归属前缀
- 入口节点先对标识进行本地预处理和目标编码提取
- 对远程目标按 `nextHopCode + nextHopDrirpUrl` 进行分组
- 同组标识合并成一个子批次，通过 DRIRP 一次性发送
- 中间节点收到子批次后重复同样的过程，直到命中目标节点
- 目标节点执行本地批量解析后，结果沿链路回传并聚合

这一方案不是逐条单跳转发，而是“分组递归转发”。

### 5.2 设计原则

- 本地优先
- 下一跳分组
- 顺序保持
- 部分成功
- 有界执行
- 可审计可观测

## 6. 总体架构设计

### 6.1 逻辑组件

建议新增以下组件：

- `IdentifierBatchResolveController`
- `IdentifierBatchResolveService`
- `DrirpBatchResolutionService`
- `BatchResolvePlanner`
- `BatchResolveAggregator`
- `BatchResolveMapper`

各组件职责如下：

| 组件 | 职责 |
| --- | --- |
| `IdentifierBatchResolveController` | 提供 REST 接口，处理 HTTP 输入输出 |
| `IdentifierBatchResolveService` | 处理请求级校验、traceId、响应包装 |
| `DrirpBatchResolutionService` | 实现跨节点批量解析主逻辑 |
| `BatchResolvePlanner` | 负责分桶、分片、下一跳规划 |
| `BatchResolveAggregator` | 负责结果聚合、回填、统计 |
| `BatchResolveMapper` | 负责 DTO 与 DRIRP Payload 映射 |

### 6.2 与现有模块的关系

本文方案直接复用以下现有能力：

- `RouteForwardDao`
- `DirectDescendantDao`
- `DrirpSecuritySupport`
- `DrirpAuditService`
- `NodeDrirpServerLifecycle`
- 本地 `DrisClient.resolveIdentifierBatch`

因此，该方案对既有系统属于“增量扩展”，而不是“推倒重来”。

## 7. 接口与协议设计

### 7.1 REST 接口设计

建议保留旧接口，并新增一个专门的跨节点接口：

- 旧接口：`POST /api/v2/identifiers/resolve/batch`
- 新接口：`POST /api/v2/identifiers/resolve/batch/distributed`

理由：

- 旧接口已经服务于本地批量解析，不应破坏兼容性
- 新接口需要更复杂的返回结构，语义上也不同于旧接口

### 7.2 请求对象

建议定义 `BatchResolveRequest`：

```json
{
  "identifiers": [
    "1100ABCD019320260101AAAAAAAAAA",
    "3701WXYZ019320260101BBBBBBBBBB"
  ],
  "resolveType": "METADATA",
  "timeoutMs": 8000,
  "ttl": 8,
  "maxParallelNodes": 8,
  "perNodeBatchSize": 100,
  "allowPartial": true,
  "traceId": "trace-batch-001"
}
```

### 7.3 响应对象

建议定义 `BatchResolveResponse`，其关键特征包括：

- 整批统计：`total/successCount/failureCount/elapsedMs`
- 单项状态：`items[]`
- 是否部分成功：`partial`
- 节点统计：`nodeStats[]`
- 输入顺序保持：`originIndex`

### 7.4 DRIRP 扩展协议

建议新增：

- `RESOLVE_BATCH_FORWARD = 7203`

对应载荷：

- `BatchResolveForwardRequestPayload`
- `BatchResolveForwardResponsePayload`

其中必须包含：

- `traceId`
- `requestId`
- `entryNodeCode`
- `senderNodeCode`
- `ttl`
- `deadlineEpochMs`
- `visitedNodeCodes`
- `items[]`

## 8. 核心算法设计

### 8.1 总体算法流程

1. 参数校验
2. identifier 去重与索引映射
3. 提取 `targetCode`
4. 划分本地项与远程项
5. 远程项按下一跳分组
6. 每组按最大批次大小切片
7. 并发发送子批次
8. 聚合子结果并恢复原始顺序
9. 输出最终结果

### 8.2 关键优化点

#### 1. 去重优化

若同一 identifier 在输入中出现多次，则只解析一次，再复制回多个位置。

#### 2. 下一跳分组优化

若多个 identifier 当前都应先发往同一个下一跳节点，则把它们合并成一个 DRIRP 子批次。

#### 3. 子批次分片优化

若某一节点分到的 identifier 数量过大，则按 `perNodeBatchSize` 分成多个子批次，避免一次消息过大。

#### 4. 结果回填优化

聚合时使用 `originIndex` 恢复顺序，避免远程返回顺序打乱客户端语义。

### 8.3 伪代码

```text
function batchResolve(request):
    validate(request)
    items = normalize(request.identifiers)
    localItems = []
    remoteBuckets = Map<NextHop, List<Item>>()

    for item in items:
        targetCode = extractTargetCode(item.identifier)
        if targetCode == selfCode:
            localItems.add(item)
        else:
            nextHop = resolveNextHop(targetCode)
            if nextHop == null:
                mark(item, ROUTE_NOT_FOUND)
            else:
                remoteBuckets[nextHop].add(item)

    localResults = resolveLocalBatch(localItems)
    remoteResults = parallelForward(remoteBuckets)
    finalResults = merge(localResults, remoteResults)
    fillMissing(finalResults)
    reorder(finalResults)
    return buildResponse(finalResults)
```

## 9. 复杂度与性能分析

### 9.1 时间复杂度

- 标识预处理：`O(N)`
- 路由分桶：`O(N)`
- 结果聚合：`O(N)`

若不考虑网络延迟，主流程时间复杂度为 `O(N)`。

### 9.2 网络复杂度

若采用逐条远程解析，则消息数近似为 `O(N * H)`，其中 `H` 是平均跳数。

而本文方案中，节点间消息数更接近：

- `O(G * H)`

其中 `G` 是按下一跳分组后的桶数，通常远小于 `N`。

这正是本文方案相对逐条单项解析的主要性能优势。

### 9.3 资源占用分析

该方案的主要资源开销来自：

- 入口节点分桶与聚合时的内存占用
- 并发远程调用的线程池占用
- 子批次序列化与反序列化开销

但这些开销都可以通过 `max-identifiers`、`max-parallel-nodes`、`per-node-batch-size` 进行控制。

## 10. 容错与安全设计

### 10.1 容错设计

应支持以下故障场景：

- 路由缺失
- 上游节点不可达
- 节点超时
- TTL 耗尽
- 环路检测失败
- 聚合结果缺失

容错策略：

- 单个子批次失败不拖垮整批请求
- 未返回项按失败状态回填
- 整批请求可 `partial=true`

### 10.2 安全设计

直接复用当前已实现的 DRIRP 安全能力：

- 消息签名
- 防重放
- 时间窗校验
- 审计日志

即：批量解析不应另起一套安全体系，而应与现有跨节点通信规则保持一致。

## 11. 与现有系统实现的匹配性分析

当前系统已经具备单条分布式解析，因此实现跨节点批量解析不需要重建基础设施。它更像是“在现有单条解析之上增加一层批量编排逻辑”。

实现匹配点如下：

- 单条路由提取逻辑可复用
- 单条远程转发协议框架可复用
- DRIRP 安全与审计能力可复用
- `RouteForwardDao` 和 `DirectDescendantDao` 可复用
- `resolveIdentifierBatch` 本地能力可直接作为目标节点上的基础执行器

这意味着本设计在工程实现上可行性较高，适合作为毕业设计的“改进型方案”。

## 13. 本文方案的创新点

可以在毕设中把创新点归纳为以下 4 点：

### 创新点 1：层级治理语义下的批量解析模型

现有经典方法要么偏单条层级解析，要么偏去中心化查找，而本文方案面向“区域-组织”双前缀体系，构建了适合治理网络的批量解析模型。

### 创新点 2：按下一跳节点分组的递归批量转发机制

相较于逐条远程解析，本文方案把远程项先按下一跳节点聚合，再递归批量下发，降低了通信放大效应。

### 创新点 3：面向工程落地的部分成功聚合返回结构

本文方案不是只返回一个列表，而是逐条保留状态、错误码、跳数和处理节点信息，更适合实际服务治理和实验分析。

### 创新点 4：在不新增核心业务表的情况下完成能力扩展

本文方案在 MVP 阶段不依赖新表，最大限度复用了现有路由、拓扑和安全机制，体现了低耦合、可演进的工程设计思想。

## 14. 实验设计与对照基线

### 14.1 建议实验目标

验证以下问题：

- 本文方案是否比逐条远程解析更快
- 在不同批量规模下，通信次数是否明显下降
- 在节点故障或路由缺失时，是否能保持更好的可用性

### 14.2 建议实验基线

建议设置以下 3 组对照：

#### Baseline 1：逐条单次分布式解析

- 每个 identifier 独立执行现有单条 `resolveDistributed`
- 这是最直接、最公平的工程基线

#### Baseline 2：广播式查询

- 入口节点向所有可能节点广播批量请求
- 理论上命中快，但通信代价最高
- 用于说明“分组路由”优于“盲目广播”

#### Baseline 3：本文方案

- 按下一跳分组
- 递归批量转发
- 分片、并发、聚合

### 14.3 指标建议

建议采集：

- 平均延迟
- P95 延迟
- 节点间请求条数
- 总网络消息数
- 成功率与部分成功率
- 路由缺失时的失败分布
- 节点超时场景下的恢复能力

### 14.4 规模建议

- 批量规模：`50 / 100 / 300 / 500`
- 节点规模：`2 / 4 / 7`
- 拓扑结构：单分支、双分支、全树型

## 15. 结论

本文围绕 DRIS 多层级节点网络中的跨节点批量解析问题，提出了一种结合“层级前缀解析”和“批量通信优化”的设计方案。与 DNS、Handle System、Chord 以及分布式查询处理中的经典方法相比，本文方案并不是简单复制某一种已有机制，而是在保持层级治理语义的前提下，将多种方法中的有效思想进行融合，形成了更适合 DRIS 场景的工程化实现路径。

从毕业设计角度看，这一方案具备以下优点：

- 有明确的研究问题
- 有可引用的相关工作基础
- 有清晰的设计创新点
- 有可实现、可测试、可对照的实验方案

因此，它非常适合作为毕设中的“详细设计 + 方法对比 + 实验设计”核心章节。
