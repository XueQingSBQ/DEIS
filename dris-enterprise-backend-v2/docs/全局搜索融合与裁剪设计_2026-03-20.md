# 全局搜索融合与裁剪设计

## 1. 调整背景

当前全局搜索的实现采用“节点内排序 + RRF 融合”的方式。该方案适合多来源结果排序尺度差异较大、需要稳妥融合的场景，但在当前系统中存在一个更突出的现实特征：

- 各节点本地检索逻辑已经基本统一
- 本地排序结果本身已经具备较好的业务准确性
- 问题主要出现在跨节点融合后，局部高质量结果被重新打乱

因此，本次调整不再让跨节点排名融合主导最终结果，而是改为“本地分数主导、跨节点命中轻量加分”的方式。

## 2. 设计目标

- 保留多节点搜索能力
- 保留结果去重能力
- 尽量直接继承各节点本地搜索的排序质量
- 避免因全局融合而破坏局部最优结果
- 按前端请求的 `limit/offset` 返回，不写死固定条数
- 对明显低质量尾部结果进行裁剪

## 3. 合并原则

### 3.1 同标识去重

全局搜索返回的多个节点结果中，可能存在同一个 `identifier` 在多个节点同时出现的情况。对同一标识，应保留一个代表结果，并补全其他节点中缺失的信息。

### 3.2 本地分数主导

对于同一标识，取所有命中结果中的最高本地分数作为主排序依据：

`bestLocalFinalScore = max(nodeResult.finalScore)`

这里的 `finalScore` 指节点本地搜索阶段已经完成重排后的最终分数。

### 3.3 跨节点命中轻量加分

若同一标识在多个节点均被检索到，可视为其具有更高的全局相关性，但该因素不应压过本地高分结果。为此只增加一个极小的重复命中奖励：

`duplicateBoost = min(0.03, 0.01 * (hitNodeCount - 1))`

### 3.4 全局得分

全局排序得分定义为：

`globalScore = bestLocalFinalScore + duplicateBoost`

其中：

- `bestLocalFinalScore` 为主导项
- `duplicateBoost` 仅为辅助项

## 4. 排序规则

全局排序按如下顺序执行：

1. `globalScore` 降序
2. `keywordScore` 降序
3. `semanticScore` 降序
4. `identifier` 升序

## 5. 裁剪规则

全局搜索结果不再固定“最多返回 5 条”，而是由前端请求的 `limit` 与 `offset` 决定返回窗口。后端只负责在该窗口范围内对明显低质量结果做裁剪。

### 5.1 基本原则

- 最终返回数不超过前端请求的 `limit`
- 若高质量结果不足，则返回数可以小于 `limit`
- 不对每个节点的返回条数做过早压缩，以免丢失真实高质量结果

### 5.2 裁剪条件

全局排序后，按以下规则裁剪尾部结果：

1. 相对阈值：结果分数低于第一名的 60% 时丢弃
2. 断崖阈值：若当前结果与上一条结果的分数比低于 0.62，则从该位置开始截断
3. 结果窗口：裁剪后结果数量最多保留到 `offset + limit`

### 5.3 保底规则

若排序后所有结果都被裁剪，但第一名结果存在，则保留第一名作为保底返回结果。

## 6. 与旧方案的区别

旧方案：

- 每个来源先独立排序
- 再通过 RRF 做主导融合
- 最终分数更多体现“多来源排名位置”

新方案：

- 每个节点本地排序结果直接保留
- 跨节点只做同标识去重与轻量加分
- 最终分数主要体现“本地最优结果质量”

## 7. 适用性判断

当前系统更适合采用新方案，原因如下：

- 各节点本地搜索字段与权重规则已经统一
- 当前业务目标是“准”，而不是“多样性优先”
- 跨节点结果量有限，且节点间业务主题相对明确
- 用户更希望看到最相关结果直接排前，而不是被融合算法平均化

## 8. 后续可扩展方向

若后续出现以下情况，可再考虑更复杂的全局融合策略：

- 节点间评分口径明显不同
- 来源数量大幅增加
- 需要更强调“多节点共同支持”的证据性排序
- 需要引入全局二阶段重排模型

在当前阶段，优先采用“本地分数主导”的全局搜索方案更符合系统目标。
