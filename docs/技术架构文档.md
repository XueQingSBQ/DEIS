# DEIS 数据基础设施标识管理系统 — 技术架构文档

## 1. 系统概述

DEIS（Data Infrastructure Identifier System）是一个面向数据基础设施的统一标识管理系统。系统以 **30 位结构化标识码** 为核心，通过 **数联网（DRIRP）分布式解析协议** 实现跨行政区划、跨机构的多模态数据资源注册、存储、解析与治理。在此基础上，系统构建了 **MCP（Model Context Protocol）智能体桥接层** 和 **DeepResearch 深度研究引擎**，使 AI Agent 能够自主编排标识解析工具、跨节点聚合证据并生成结构化研究报告。

整体架构分为三层：

```
┌─────────────────────────────────────────────────────────────────────┐
│  第三层：智能研究交互层                                                │
│  DeepResearch Orchestrator (规划-执行-报告) + Vue 3 研究工作台         │
├─────────────────────────────────────────────────────────────────────┤
│  第二层：AI 能力适配层                                                │
│  MCP Server (9 个工具 / 2 个资源 / 2 个提示词模板)                    │
├─────────────────────────────────────────────────────────────────────┤
│  第一层：核心业务能力层                                                │
│  企业后端 (标识·资源·搜索·审计) + DRIRP 数联网 (gRPC 分布式解析)       │
│  认证中心 (JWT RS256) + 对象存储 (COS/S3/Local) + 向量索引            │
└─────────────────────────────────────────────────────────────────────┘
```

## 2. 多模态数据的数联网存储与管理

### 2.1 统一标识编码体系

系统为每一项数据资源分配一个 **30 位定长标识码**，编码结构如下：

```
位置:   1-4     5-8      9-10   11   12    13-20       21-29     30
       ┌──────┬──────┬──────┬────┬────┬──────────┬──────────┬──────┐
       │ 区域  │ 机构  │ 行业 │数据│注册│   日期    │  凭证     │校验位│
       │ 4位   │ 4位  │ 2位  │类别│类型│  8位     │  9位     │ 1位  │
       └──────┴──────┴──────┴────┴────┴──────────┴──────────┴──────┘
```

| 字段 | 长度 | 说明 | 示例 |
|------|------|------|------|
| 区域码 | 4 位数字 | 行政区划代码 | `1100`（北京）、`3100`（上海） |
| 机构码 | 4 位大写字母 | A–H, J–N, P–Z（排除 I 和 O 以避免歧义） | `CNTA` |
| 行业码 | 2 位数字 | 01=能源, 02=交通, 03=卫生, 04=金融… | `02` |
| 数据类别 | 1 位数字 | 1=原始数据, 2=衍生数据, 3=模型, 9=其他 | `1` |
| 注册类型 | 1 位数字 | 1=临时, 2=正式, 3=归档 | `2` |
| 日期 | 8 位数字 | 注册日期 `yyyyMMdd` | `20260320` |
| 凭证 | 9 位 Base32 | 随机生成，字符集 0–9 A–Z（排除 I 和 O） | `A3B7C9D2E` |
| 校验位 | 1 位 | mod-34 加权校验 | `F` |

标识码的**前 8 位**（区域码 + 机构码）构成**目标码（Target Code）**，是数联网路由解析的关键——系统据此判断该标识归属哪个节点，从而决定本地解析还是跨节点转发。

SDK 采用 DDD（领域驱动设计），核心领域对象为：

- **`IdentifierCode`** — 标识编码值对象，封装编解码与校验逻辑
- **`IdentifierMetadata`** — 标识元数据，描述数据资源的名称、行业、类别等属性
- **`Resource`** — 绑定的资源组件（详见 2.3 节）
- **`DigitalObject`** — 聚合根，将标识、元数据与资源组件聚合为一个完整的数字对象

### 2.2 多模态数据的存储模型

系统支持的"多模态数据"涵盖文档、数据集、图像、工具包和 API 服务等多种类型。存储架构采用**元数据与对象数据分离**的设计：

```
┌───────────────────────────────────────────────────────────┐
│                     MySQL 数据库                           │
│  ┌────────────────────┐    ┌──────────────────┐           │
│  │ identifier_metadata │───▶│    resource       │          │
│  │   (标识元数据)       │1:1 │  (当前组件绑定)    │          │
│  └────────┬───────────┘    └──────┬───────────┘           │
│           │                       │                       │
│  ┌────────▼───────────┐    ┌──────▼───────────┐           │
│  │ identifier_vector   │    │ resource_version  │          │
│  │ _index (向量索引)    │    │ (版本历史，不可变)  │          │
│  └────────────────────┘    └──────────────────┘           │
│                                                           │
│  ┌────────────────────┐    ┌──────────────────┐           │
│  │ dris_route_forward  │    │ identifier_history│          │
│  │   (路由转发表)       │    │   (审计日志)       │          │
│  └────────────────────┘    └──────────────────┘           │
└───────────────────────────────────────────────────────────┘
                         │
                    locator 引用
                         ▼
┌───────────────────────────────────────────────────────────┐
│               对象存储层 (COS / S3 / Local)                 │
│                                                           │
│   cos://bucket/identifiers/{id}/resource/up-xxx.pdf       │
│   cos://bucket/identifiers/{id}/tool/up-xxx.zip           │
│   local://local-bucket/identifiers/{id}/resource/up-xxx.csv│
│   https://api.example.com/v1/openapi.json                 │
└───────────────────────────────────────────────────────────┘
```

**MySQL 存储内容**：

| 表名 | 存储内容 | 主键 |
|------|----------|------|
| `identifier_metadata` | 标识元数据：30 位标识码、区域、机构、行业、数据类别、名称、描述、所有者、状态、乐观锁版本号等 | `identifier` (30位) |
| `resource` | 当前资源绑定：组件类型、存储方式、访问方法、内容类型、格式、定位符（locator）、文件大小、哈希值 | `identifier` (1:1 外键) |
| `resource_version` | 不可变的资源版本历史：每次绑定变更追加一条记录，支持版本回溯 | 自增 ID |
| `upload_session` | 文件上传会话状态机（init → committing → done/failed/expired） | `upload_id` |
| `identifier_vector_index` | 128 维向量嵌入，用于语义搜索 | `identifier` |

**对象存储层存储内容**：所有实际的文件字节（PDF、CSV、JSON、图像、工具 ZIP 包等）。MySQL 中的 `resource.locator` 字段以 URI 形式指向对象存储位置。

### 2.3 三类组件模型

系统将多模态数据抽象为三类**组件（Component）**，以统一的 `Resource` 领域模型管理：

| 组件类型 | 典型内容 | 上传方式 | 支持的格式 | 存储位置 |
|----------|----------|----------|-----------|----------|
| **resource**（数据资源） | 文档、数据集、图像、通用文件 | 预签名 URL 直传至对象存储 | PDF, DOCX, JSON, JSONL, CSV, Parquet, XLSX, PNG, JPEG, WebP, 通用二进制 | COS/S3/Local |
| **tool**（工具能力） | 可执行工具包 | 预签名 URL 直传，需 SHA-256 校验 | ZIP | COS/S3/Local |
| **service**（服务/API） | API 服务描述 | 直接绑定（PUT 接口），不经过上传会话 | OpenAPI JSON, OpenAPI YAML | 定位符为 HTTPS URL |

`Resource` 域模型核心字段：

```
Resource {
    componentType   : "resource" | "tool" | "service"  // 组件类型
    storageType     : "cos" | "s3" | "local"           // 存储后端
    accessMethod    : "download" | ...                  // 访问方式
    contentType     : "doc" | "dataset" | "image" | "tool" | "service"  // 语义分类
    format          : "pdf" | "csv" | "json" | "zip" | "openapi_json"   // 格式
    locator         : "cos://bucket/key" | "https://..."  // 统一资源定位符
    size            : long                             // 文件大小（字节）
    hashValue       : "sha256:..."                     // 完整性哈希
    extra           : Map<String, Object>              // 扩展属性（bucket, objectKey, profile 等）
}
```

这一模型使得一个标识码能够统一关联文档、数据集、图像、可执行工具或 API 服务等任意类型的数据资源，实现了**多模态数据的统一标识与管理**。

### 2.4 文件上传与下载流程

文件上传采用**两阶段预签名 URL 直传**架构，后端不经手文件流，降低服务端带宽压力：

```
阶段一：创建上传会话
  客户端 ──POST /upload-sessions──▶ 后端
  后端：
    1. 校验标识存在且未删除
    2. 确定上传 Profile（推断 componentType、contentType、format）
    3. 生成 upload_id（格式: up-{timestamp}-{random12}）
    4. 计算对象键: identifiers/{identifier}/{resource|tool}/{uploadId}.{ext}
    5. 向对象存储网关申请预签名 PUT URL
    6. 持久化 upload_session 记录（status=init）
  后端 ──返回 presigned URL──▶ 客户端

阶段二：直传与确认
  客户端 ──PUT 文件──▶ 对象存储（COS/S3/Local）
  客户端 ──POST /complete──▶ 后端
  后端：
    1. 检查会话未过期、状态为 init
    2. UploadObjectVerifier 向对象存储查询 SHA-256 和文件大小
    3. 构建 Resource 对象（locator=cos://bucket/key）
    4. 原子更新 resource 表（当前绑定）+ 追加 resource_version 行（版本历史）
    5. 标记 identifier_metadata.vector_dirty=1（触发向量重索引）
    6. 更新 upload_session 状态为 done
```

文件下载同样通过预签名 URL 实现：
- 对于 `cos://` 或 `local://` 定位符：从 `resource.extra` 提取 bucket/objectKey，生成预签名 GET URL
- 对于 `https://` 定位符：直接返回该 URL
- `service` 类型组件和 `local_exec` 工具不支持下载

### 2.5 数联网分布式解析（DRIRP）

#### 2.5.1 层级拓扑架构

系统支持 **国家 → 省 → 市 → 县** 四级层级化多节点部署，每个节点拥有独立数据库、独立端口：

```
                node1-country (根节点)
                8200 / gRPC 19200
                        │
                node2-province
                8201 / gRPC 19201
                    ┌───┴───┐
            node3-city-a   node5-city-b
            8202/19202     8204/19204
                │              │
          node4-county-a  node6-county-b
          8203/19203      8205/19205
```

节点之间通过 DRIRP（Data Resource Identifier Resolution Protocol）gRPC 通道通信。协议基于统一消息信封 `DrirpMessage`：

```protobuf
message DrirpMessage {
    int32  code;            // 操作码（resolve / batch / search / operation）
    string rid;             // 请求标识
    string body;            // JSON 载荷
    int64  ts;              // 时间戳
    string auth;            // HMAC-SHA256 签名
    string traceId;         // 链路追踪 ID
    string nonce;           // 防重放随机数
    string idempotencyKey;  // 幂等键
}
```

协议保障机制：

| 特性 | 实现方式 |
|------|----------|
| 身份认证 | HMAC-SHA256 签名 + Nonce 防重放 |
| 幂等重试 | 基于 idempotencyKey，相同键的重复请求返回缓存结果 |
| 弹性保护 | 熔断器（Circuit Breaker）+ 限流器（Rate Limiter） |
| 环路检测 | visitedUrls 列表 + TTL 跳数限制（默认最大 8 跳） |

#### 2.5.2 解析路由机制

分布式解析的核心是**基于目标码的路由转发**：

```
解析请求到达某节点
      │
      ▼
提取标识前 8 位 → 目标码 (targetCode = 区域码 + 机构码)
      │
      ├── targetCode == 本节点 nodeCode → 本地 MySQL 查询 → 返回结果
      │
      └── targetCode ≠ 本节点 nodeCode → 路由查找
              │
              ├── 查询 dris_route_forward 表（显式路由）
              ├── 查询 dris_direct_descendant 表（子节点匹配）
              └── 回退到父节点 URL（若 resolveAllowParentFallback 启用）
              │
              ▼
         确定下一跳节点
              │
         ┌────┴────┐
    递归模式      迭代模式
         │           │
    转发请求给     返回下一跳地址
    下一跳节点     给客户端重新发起
    (逐跳递归)    (客户端自驱循环)
```

#### 2.5.3 批量分布式解析

批量解析是 DeepResearch 的核心数据采集手段：

1. **按目标码分组**：将一批标识按前 8 位分组，相同目标码的标识路由到同一个节点
2. **并行异步执行**：为每个分组启动 `CompletableFuture` 异步任务
3. **本地组直接查询**：目标码匹配本节点的分组直接查 MySQL
4. **远程组 DRIRP 转发**：其余分组通过 gRPC 批量转发给目标节点
5. **结果合并**：汇总所有分组的解析结果，标记每一项的成功/失败/来源节点

这一机制使得 DeepResearch 能够仅通过一次批量调用就跨越多个节点收集标识元数据、数字对象和资源组件信息。

### 2.6 搜索与语义检索

搜索引擎支持三种模式：

| 搜索模式 | 实现原理 | 适用场景 |
|----------|----------|----------|
| **KEYWORD** | MySQL 模糊匹配（名称、描述、所有者等多字段） | 精确关键词查找 |
| **SEMANTIC** | 128 维向量余弦相似度搜索（identifier_vector_index 表） | 语义近似查找 |
| **HYBRID** | 关键词评分 + 语义评分联合重排（ReRanker） | 兼顾精确与语义 |

**向量索引同步机制**（基于脏标记模式）：

1. 标识元数据变更时，`identifier_metadata.vector_dirty` 被置为 1
2. `VectorIndexAutoSyncScheduler` 每 3 秒扫描脏记录（每批最多 1000 条）
3. `VectorMetadataDocumentBuilder` 将元数据各字段拼接为文本文档
4. `EmbeddingProvider` 生成 128 维向量嵌入
5. UPSERT 至 `identifier_vector_index` 表，清除脏标记
6. 若有更新，自动清除搜索结果缓存

**分布式全局搜索**采用两阶段扇出策略：

1. **LOCATE_ANCHOR**：沿路由树导航到锚点节点
2. **SEARCH_SUBTREE**：从锚点向所有子孙节点扇出搜索，使用 RRF（Reciprocal Rank Fusion, k=60）合并多节点结果

## 3. DeepResearch 深度研究引擎设计

### 3.1 设计定位与核心思想

DeepResearch 是构建在数联网标识管理能力之上的**领域智能体（Domain Agent）**。其核心思想是：

> **将标识解析能力通过 MCP 协议暴露为 AI 可调用工具，由编排器自主规划研究策略、执行跨节点证据采集、生成结构化研究报告。**

设计原则：
- **非侵入式**：MCP Server 和 DeepResearch Orchestrator 不修改核心后端，仅消费其 REST API
- **LLM 可选**：系统在无 LLM 时完全可用（启发式规划器 + 规则化报告），LLM 仅增强规划智能和摘要质量
- **先报告后摘要**：结构化报告在工具执行完成后立即生成并推送，LLM 摘要作为异步增强流式追加
- **双模式执行**：用户可选择后端编排（Agent 模式）或浏览器直连 MCP（Manual 模式）

### 3.2 系统架构与数据流

### 3.3 MCP 工具层

MCP Server 将核心后端能力封装为 **9 个只读、幂等的 MCP 工具**，供 AI Agent 调用：

| 工具名 | 功能 | 后端 API |
|--------|------|----------|
| `resolve_metadata` | 解析单个标识的元数据 | `GET /api/v2/identifiers/{id}/metadata` |
| `resolve_object` | 解析单个标识的完整数字对象 | `GET /api/v2/identifiers/{id}/object` |
| `resolve_component` | 解析单个标识的资源组件 | `GET /api/v2/identifiers/{id}/component` |
| `batch_resolve_metadata_distributed` | 跨节点批量元数据解析 | `POST /api/v2/identifiers/resolve/batch/distributed` |
| `batch_resolve_object_distributed` | 跨节点批量对象解析 | `POST /api/v2/identifiers/resolve/batch/object/distributed` |
| `batch_resolve_component_distributed` | 跨节点批量组件解析 | `POST /api/v2/identifiers/resolve/batch/component/distributed` |
| `search_global` | 分布式全局搜索 | `POST /api/v2/search/global` |
| `query_audit_logs` | 审计日志查询 | `GET /api/v2/audit/identifier-history` |
| `get_node_routes` | 获取节点路由拓扑 | `GET /api/v2/node/routes` |

MCP Server 还注册了：
- **2 个资源**：`dris://system/capabilities`（系统能力概览）、`dris://node/topology`（拓扑快照）
- **2 个提示词模板**：`cross_node_batch_analysis`（跨节点分析引导）、`identifier_provenance_analysis`（标识溯源引导）

传输协议采用 **MCP Streamable HTTP**（`/mcp` 端点），基于 JSON-RPC 2.0，通过 `mcp-session-id` 管理会话。所有工具标注 `readOnlyHint: true` 和 `idempotentHint: true`，确保安全重试。

### 3.4 研究模板系统

DeepResearch 定义了 **4 种研究模板**，每种模板对应一套固定的工具调用序列：

| 模板 ID | 名称 | 适用场景 | 前置条件 |
|---------|------|----------|----------|
| `discovery_overview` | 研究总览 | 从自然语言问题出发，搜索 → 批量解析 → 审计 | 需要问题文本 |
| `identifier_compare` | 标识对比 | 多个标识的并行多维证据分析与比较 | 需要多个标识 |
| `audit_trace` | 审计追踪 | 单个标识的全生命周期追踪回放 | 需要一个标识 |
| `anchor_search` | 锚点搜索 | 从指定节点出发搜索并解析发现的标识 | 需要问题文本 + 锚点节点 |

每种模板的工具调用序列：

```
discovery_overview / anchor_search:
  ① get_node_routes
  ② search_global (搜索发现标识)
  ③ batch_resolve_metadata_distributed
  ④ batch_resolve_object_distributed
  ⑤ batch_resolve_component_distributed
  ⑥ query_audit_logs (×3，前三个标识各查一次)

identifier_compare:
  ① get_node_routes
  ② batch_resolve_metadata_distributed
  ③ batch_resolve_object_distributed
  ④ batch_resolve_component_distributed
  ⑤ query_audit_logs (×3)

audit_trace:
  ① get_node_routes
  ② resolve_metadata
  ③ resolve_object
  ④ resolve_component
  ⑤ query_audit_logs
```

### 3.5 Planner 规划器：双模式决策

#### 3.5.1 启发式规划器

启发式规划器（`heuristicPlanner.ts`，487 行）不依赖任何外部 LLM，通过多步规则推理完成研究规划：

**第一步：标识提取**
- 从用户输入的标识文本中按空格/逗号/分号分割
- 从问题文本中用正则 `/\b[0-9A-Za-z]{16,}\b/g` 提取 16+ 位字母数字串
- 去重后作为显式标识列表

**第二步：搜索意图构建**
- **锚点推断**：从问题中检测完整节点码（如 `1100CNTA`）或 4 位区域码
- **实体类型过滤**：关键词匹配推断过滤器（"数据集"→dataset, "设备"→device, "服务"→service, "工具"→tool）
- **格式过滤**：检测格式关键词（csv, json, xml, pdf, parquet 等）
- **关键词提取**：中英文分词 → 去停用词（支持中英文双语停用词表）→ 去除已匹配的过滤器和节点码 → 截取前 8 个关键词

**第三步：模板选择**（优先级决策树）

```
有锚点节点码？ ──是──▶ anchor_search
       │
       否
       │
多个标识 + 对比意图词（"compare", "vs", "差异", "对比"）？ ──是──▶ identifier_compare
       │
       否
       │
有标识 + 审计意图词（"audit", "history", "审计", "追溯"）？ ──是──▶ audit_trace
       │
       否
       │
多个标识（无特殊意图）？ ──是──▶ identifier_compare
       │
       否
       │
单个标识 + 无问题？ ──是──▶ audit_trace
       │
       否
       │
有自然语言问题？ ──是──▶ discovery_overview
       │
       否
       │
兜底 ──▶ discovery_overview
```

**第四步：参数规范化**
- `limit` 限制在 1–20，`ttl` 限制在 1–16
- 填充默认搜索模式（KEYWORD）和策略（ITERATIVE）
- 生成有序的 `PlanStep[]` 列表

#### 3.5.2 LLM 规划器

LLM 规划器（`llmPlanner.ts`，72 行）在启发式规划的基础上引入 LLM 决策：

1. 先运行启发式标识提取和模板选择作为**上下文和 fallback**
2. 构造系统提示词，指示 LLM 作为 "DRIS DeepResearch 的领域规划器"
3. 将用户问题、提取的标识、锚点节点、启发式 fallback 一并发送给 LLM
4. 使用 **Zod Schema** 严格校验 LLM 返回的 JSON 结构：
   ```typescript
   {
     templateId: "discovery_overview" | "identifier_compare" | "audit_trace" | "anchor_search",
     rationale: string[1..6],           // 选择理由（1-6 条）
     explicitIdentifiers?: string[0..12] // LLM 修正后的标识列表
   }
   ```
5. LLM 建议的标识合并至启发式提取的列表
6. 使用 LLM 选择的模板调用相同的步骤构建逻辑

#### 3.5.3 Auto 模式

生产环境默认使用 Auto 模式：
```
Auto 模式：
  尝试 LLM 规划 → 成功则使用 LLM 结果
                 → 失败（超时/解析错误/API 不可用）则自动降级为启发式规划
```

### 3.6 Executor 执行引擎

执行引擎（`runPlan.ts`，380 行）逐步执行研究计划，每一步调用一个 MCP 工具：

```
executeResearchPlan(plan, form, mcpClient, onStep)
  │
  ├── 1. 列举 MCP Server 可用工具
  │
  ├── 2. 发射 "agent_plan" 合成步骤（展示模板选择理由）
  │
  ├── 3. 调用 get_node_routes 获取拓扑
  │
  ├── 4. [若搜索模板] 调用 search_global
  │       │
  │       ├── 从搜索结果中提取标识
  │       │   （检查 identifier / identifierValue / pid / id 等键）
  │       │
  │       ├── 合并显式标识与搜索发现的标识（去重，上限 8 个）
  │       │
  │       └── 若无标识可聚焦 → 发射 "skipped" 步骤并结束
  │
  ├── 5. [批量模板] 依次调用：
  │       batch_resolve_metadata_distributed
  │       batch_resolve_object_distributed
  │       batch_resolve_component_distributed
  │       query_audit_logs (×3, 前 3 个标识)
  │
  └── 6. [审计追踪模板] 依次调用：
          resolve_metadata → resolve_object → resolve_component → query_audit_logs
```

**每一步**都生成 `ToolExecutionStep`，包含：
- `id`：步骤唯一标识
- `toolName`：MCP 工具名
- `status`：pending → running → success/error/skipped
- `startedAt` / `completedAt`：起止时间
- `durationMs`：耗时
- `args`：调用参数
- `result`：原始返回
- `summary`：人类可读的摘要（如 "搜索返回 5 条结果" "成功解析 3/5，失败 2"）
- `error`：错误信息

步骤通过 `onStep` 回调实时推送给服务层，服务层再通过 SSE 推送给前端。

### 3.7 Report Builder 报告生成器

报告生成器（`buildReport.ts`，1020 行）是最核心的分析逻辑，将所有工具执行结果合并为统一的研究报告。

#### 3.7.1 ResourceLandscape 资源全景图

报告生成的第一步是构建 **ResourceLandscape**——将来自搜索、元数据解析、对象解析、组件解析、审计日志等多个工具的输出融合为统一视图：

```typescript
ResourceLandscape {
    searchItems:    SearchItem[]        // 搜索发现的条目
    profiles:       ResourceProfile[]   // 按标识聚合的资源画像
    auditRecords:   AuditRecord[]       // 审计记录
    visitedNodeCodes: string[]          // 涉及的节点
    failedNodes:    string[]            // 失败的节点
    metadataStats:  { resolved, failed } // 元数据解析统计
    objectStats:    { resolved, failed } // 对象解析统计
    componentStats: { resolved, failed } // 组件解析统计
    routeCount:     number              // 路由条数
}
```

**ResourceProfile** 是核心实体（30+ 字段），为每个标识聚合来自所有工具的信息：

```
ResourceProfile {
    // 身份信息（来自 metadata）
    identifier, name, description, owner, industry, dataCategory, registrationType, entityType

    // 节点信息（来自 batch resolve/search）
    sourceNodeCode, targetNodeCode, resolvedByNodeCode

    // 解析状态
    metadataStatus, objectStatus, revision, hasMetadata, hasObject, hasComponent

    // 组件详情（来自 component）
    componentType, storageType, accessMethod, contentType, format, locator, size

    // 审计信息（来自 audit_logs）
    auditCount, auditFailureCount, lastAuditOperation, lastAuditTime

    // 搜索排名（来自 search）
    searchScore, searchRank

    // 资源分类（推断得出）
    classifiedType  // "服务/API" | "工具能力" | "可下载数据" | "可定位资源" | "待确认"
}
```

**Profile 合并算法**：

1. 遍历搜索结果 → 以标识为键创建/更新 ResourceProfile
2. 遍历批量元数据解析结果 → 合并元数据字段
3. 遍历批量对象解析结果 → 合并数字对象字段和嵌套资源
4. 遍历批量组件解析结果 → 合并组件绑定信息
5. 遍历审计记录 → 按标识累计审计计数
6. 按搜索评分（降序）→ 完整度 → 搜索排名排序

#### 3.7.2 资源分类

根据组件类型、访问方式、存储类型和定位符自动将资源分为 5 类：

```
componentType == "service"                    → "服务/API"
componentType == "tool"                       → "工具能力"
accessMethod == "download" 且有 locator        → "可下载数据"
有 locator                                    → "可定位资源"
其他                                          → "待确认"
```

#### 3.7.3 证据卡片

为每个 ResourceProfile 生成 **EvidenceCard**（最多 10 张），每张卡片包含：

```typescript
EvidenceCard {
    title:    string              // 资源名称或标识
    subtitle: string              // 分类标签 + 行业
    tone:     "neutral" | "good" | "warn" | "bad"  // 基于完整度着色
    metrics:  Array<{label, value}>  // 结构化指标（标识码、行业、格式、访问方式等）
    bullets:  string[]             // 要点列表
}
```

此外还生成两张全局卡片：
- **跨节点发现概览**：涉及的节点数、路由条数、批量解析统计
- **审计治理概览**：审计记录总数、失败比例、最近操作

#### 3.7.4 摘要章节

报告按以下章节结构组织：

| 章节 | 内容 |
|------|------|
| 研究目标 | 用户问题 + 模板 + 聚焦标识数量 |
| 发现范围 | 搜索模式、策略、返回条目数 |
| 资源格局 | 行业分布、格式分布、节点分布统计 |
| 重点资源画像 | 前 5 个 ResourceProfile 的详细描述 |
| 资源内容样本 | 内容预览（CSV 表头、JSON 结构、HTML 标题等） |
| 跨节点证据 | 批量解析成功/失败率、涉及节点 |
| 审计与治理信号 | 审计记录概况、失败事件 |
| 结论 | 综合评估 |

最终报告同时生成 Markdown 格式文本，支持导出。

### 3.8 资源内容预览

资源预览模块（`resourcePreview.ts`，568 行）在报告生成后，对发现的资源进行轻量级内容采样：

1. **候选筛选**：从组件和对象解析结果中收集 HTTP 定位符，按搜索评分排序，取前 3 个
2. **内容获取**：使用 `Range: bytes=0-4095` HTTP 头仅下载前 4KB
3. **格式检测与解析**：

| 格式 | 检测方式 | 预览内容 |
|------|----------|----------|
| CSV | Content-Type 或扩展名 | 表头行 + 前 2 行样本数据 |
| JSON | Content-Type 或扩展名 | 顶层键名或数组长度 + 首元素结构 |
| HTML | Content-Type | `<title>` + `<meta description>` + body 文本片段 |
| XML | Content-Type | 根标签 + 前 4 行 |
| 纯文本 | 兜底 | 前 4 行 |
| 二进制 | ZIP 魔数 `0x504B` / OLE 魔数 `0xD0CF11E0` | 标注为二进制文件 |

4. **并发控制**：使用 `mapWithConcurrency()` 限制同时获取数为 2

### 3.9 LLM 执行摘要

LLM 摘要生成器（`llmSummary.ts`，99 行）在结构化报告生成后提供增值摘要：

- **系统提示词**：指示 LLM 聚焦"主题相关数据资源、跨节点覆盖、可用性和治理证据"
- **输入上下文**：规划器信息、报告章节（SummarySection[]）、证据卡片（最多 8 张）、工具执行步骤摘要
- **输出**：2–5 条要点总结，以用户问题的语言回应
- **双模式**：支持批量（`generateExecutiveSummary`）和流式（`generateExecutiveSummaryStream`）生成
- **流式模式**：通过 SSE `summary_delta` 事件实时推送每个文本增量

摘要生成后通过 `prependExecutiveSummary()` 插入报告首部作为"LLM 执行摘要"章节。

### 3.10 SSE 流式协议

DeepResearch 采用 **Server-Sent Events** 实现渐进式结果推送，定义了 7 种事件类型：

```
event: meta          data: { plannerMode, llmModel, mcpUrl }
event: plan          data: { templateId, rationale[], steps[] }
event: step          data: { step: ToolExecutionStep }        ← 每步实时推送
event: report        data: { report: ResearchReport }         ← 工具执行完成后推送
event: summary_delta data: { delta: "..." }                   ← LLM 摘要流式增量
event: done          data: { focusedIdentifiers, durationMs }
event: error         data: { message: "..." }
```

这一设计实现了**先结构后摘要**的渐进披露策略：用户在工具执行期间就能看到实时时间线，工具执行完成后立即看到证据卡片和报告章节，最后 LLM 摘要以打字效果逐字出现。

### 3.12 端到端执行流程

以用户提问"总结新能源大数据的跨区域共享情况"为例：

```
1. 用户在研究工作台输入问题，选择 Agent 模式，点击"开始智能研究"

2. 前端 POST /api/research/stream → Orchestrator

3. Orchestrator 规范化请求（clamp limit=5, 默认搜索模式=KEYWORD）

4. Planner（Auto 模式）：
   a. 尝试 LLM 规划器 → 发送问题给 LLM
   b. LLM 返回 { templateId: "discovery_overview", rationale: ["问题是开放性研究...", "需要全局搜索发现资源..."] }
   c. Zod 校验通过 → 使用 LLM 结果
   d. （若 LLM 超时 → 自动降级为启发式：提取关键词"新能源""大数据""跨区域""共享"，推断行业=能源，选择 discovery_overview）

5. 发射 SSE: meta, plan

6. 连接 MCP Server，逐步执行：
   ① get_node_routes → 获取 6 节点拓扑           [SSE: step ✓ 0.1s]
   ② search_global("新能源 大数据 共享", 行业=能源) [SSE: step ✓ 1.8s]
      → 发现 5 个标识
   ③ batch_resolve_metadata_distributed(5 个标识) [SSE: step ✓ 0.9s]
      → 跨 3 个节点解析，4 成功 1 失败
   ④ batch_resolve_object_distributed             [SSE: step ✓ 0.7s]
   ⑤ batch_resolve_component_distributed          [SSE: step ✓ 0.5s]
   ⑥ query_audit_logs(标识1)                      [SSE: step ✓ 0.2s]
   ⑦ query_audit_logs(标识2)                      [SSE: step ✓ 0.2s]
   ⑧ query_audit_logs(标识3)                      [SSE: step ✓ 0.1s]

7. Report Builder：
   a. 构建 ResourceLandscape（合并 5 个 ResourceProfile）
   b. 分类资源：2 个可下载数据、1 个服务/API、1 个工具能力、1 个待确认
   c. 生成 7 个摘要章节 + 5 张证据卡片 + 2 张全局卡片
   d. 渲染 Markdown

8. 发射 SSE: report（第一版报告，用户立即可见证据卡片）

9. 资源内容预览：
   a. 选取 2 个 HTTP 定位符
   b. Range 请求获取前 4KB
   c. 识别 CSV → 提取表头和样本行
   d. 重建报告，插入"资源内容样本"章节

10. 发射 SSE: report（更新版报告）

11. LLM 执行摘要（流式）：
    a. 将报告章节和证据卡片发送给 LLM
    b. LLM 流式返回 3 条要点总结
    c. 每个 token 发射 SSE: summary_delta

12. 发射 SSE: report（最终版报告，含 LLM 摘要）

13. 发射 SSE: done（总耗时 5.7 秒）
```
