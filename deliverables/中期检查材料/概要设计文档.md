# 数据基础设施标识管理系统概要设计文档

## 1. 文档说明

### 1.1 编写目的

本文档用于在需求分析基础上，对系统总体架构、模块划分、数据模型、关键流程、部署方式和扩展策略进行说明，作为详细设计、编码实现、系统测试和论文第四章撰写的基础。

### 1.2 设计原则

1. 统一模型，分层实现。
2. 核心规则与具体业务解耦。
3. 业务流程完整，但数据库修改尽量最小化。
4. 多节点解析机制可运行、可测试、可对比。
5. 模块边界清晰，便于后续迁移和重构。

## 2. 总体架构设计

### 2.1 架构目标

系统整体要解决两个层面的问题：

1. 在单节点内，完成标识生成、元数据管理、资源绑定、解析、搜索和治理。
2. 在多节点间，完成节点接入、路由传播、跨节点解析、跨节点搜索和能力开放。

因此，系统采用“核心 SDK + 协议 SDK + 业务后端 + 认证中心 + 开放接入层 + 可视化前端”的多模块结构。

### 2.2 总体模块构成

系统由以下核心模块构成：

1. `dris-java-sdk-next`
2. `drirp-java-sdk`
3. `dris-enterprise-backend-v2`
4. `dris-auth-center`
5. `dris-mcp-server`
6. `dris-deepresearch-orchestrator`
7. `dris-deepresearch-frontend`

### 2.3 各模块职责

#### 2.3.1 `dris-java-sdk-next`

定位：标识核心能力 SDK。

主要职责：

1. 标识编码规则定义
2. 标识生成与格式校验
3. 核心模型定义
4. 与具体数据库无关的基础能力

设计取舍：

1. 不再承载完整业务服务流程
2. 不直接依赖具体数据库 DAO
3. 保留最核心、最可复用的规则能力

#### 2.3.2 `drirp-java-sdk`

定位：跨节点通信协议 SDK。

主要职责：

1. DRIRP 消息模型定义
2. 请求响应编解码
3. 客户端与服务端通信支持
4. 出站连接复用
5. 节点间调用基础设施

设计取舍：

1. 不负责业务判断
2. 不直接处理标识解析业务规则
3. 只提供稳定的跨节点消息通道

#### 2.3.3 `dris-enterprise-backend-v2`

定位：业务后端核心。

主要职责：

1. 标识注册、更新、删除、解析
2. 元数据管理
3. 资源绑定与下载签名
4. 节点注册、拓扑维护和路由维护
5. 搜索、批量解析、审计
6. 对前端、MCP、DeepResearch 提供统一接口

#### 2.3.4 `dris-auth-center`

定位：统一认证中心。

主要职责：

1. 用户注册
2. 用户登录
3. JWT 令牌签发
4. 公钥发布与用户信息查询

#### 2.3.5 `dris-mcp-server`

定位：面向智能体的工具接入层。

主要职责：

1. 封装搜索工具
2. 封装元数据解析工具
3. 封装数字对象解析工具
4. 封装审计查询等治理工具

#### 2.3.6 `dris-deepresearch-orchestrator`

定位：研究任务编排层。

主要职责：

1. 接收研究任务
2. 进行任务规划
3. 调用后端和 MCP 能力
4. 汇总结果并输出报告

#### 2.3.7 `dris-deepresearch-frontend`

定位：系统演示与研究交互前端。

主要职责：

1. 展示节点拓扑
2. 完成标识注册与资源绑定
3. 展示解析、搜索、审计等页面
4. 提供研究型任务交互界面

## 3. 分层设计

### 3.1 核心规则层

由 `dris-java-sdk-next` 承载。

包含内容：

1. 核心模型
2. 枚举与规则
3. 标识生成器
4. 标识格式校验器

特点：

1. 高复用
2. 低耦合
3. 与具体后端实现解耦

### 3.2 协议通信层

由 `drirp-java-sdk` 承载。

包含内容：

1. 消息定义
2. 请求封装
3. 响应封装
4. 通信客户端
5. 通信服务端适配

### 3.3 业务编排层

由 `dris-enterprise-backend-v2` 承载。

包含内容：

1. Controller 接口层
2. Service 业务编排层
3. Repository/Mapper 数据访问层
4. 任务执行器
5. 节点路由与解析协调层

### 3.4 治理与安全层

由认证中心和后端认证拦截器共同组成。

包含内容：

1. 登录认证
2. 写接口保护
3. 审计记录
4. 节点鉴权扩展预留

### 3.5 应用接入层

由 MCP、DeepResearch 和 Web 前端组成。

包含内容：

1. 页面化交互
2. 自然语言研究任务
3. 智能体工具调用
4. 展示与答辩支撑

## 4. 核心数据模型设计

### 4.1 数字对象模型

系统把数据要素统一建模为数字对象。数字对象是系统最核心的业务对象，其结构由三部分组成：

1. 标识
2. 元数据
3. 资源

设计意义：

1. 标识解决唯一引用问题
2. 元数据解决描述问题
3. 资源解决实体访问和能力调用问题

### 4.2 标识模型

标识由地区码、机构码、时间片段、业务规则编码等信息组合而成。

主要要求：

1. 唯一性
2. 可校验性
3. 可读性
4. 可映射到所属节点

### 4.3 元数据模型

元数据模型至少包含以下字段：

1. `identifier`
2. `name`
3. `description`
4. `industry`
5. `dataCategory`
6. `registrationType`
7. `applicationScenario`
8. `owner`
9. `entityType`
10. `additionalAttributes`

这些字段既是注册输入，也是搜索、解析、展示和研究任务的基础数据源。

### 4.4 资源模型

资源模型用于描述与数字对象关联的实际内容或能力，设计时明确区分：

1. `resource`：真实数据文件
2. `tool`：可调用工具能力
3. `service`：可访问服务接口

资源模型中的关键属性包括：

1. `storageType`
2. `locator`
3. `mediaType`
4. `fileName`
5. `description`
6. `resourceType`

### 4.5 上传会话模型

上传会话作为文件资源绑定的中间过程模型，主要用于：

1. 创建上传入口
2. 记录上传状态
3. 在上传完成后完成资源绑定

### 4.6 节点模型

节点模型用于表达系统中的业务节点，至少包含：

1. 节点编码
2. 节点名称
3. 节点层级
4. 父节点信息
5. DRIRP 地址
6. HTTP 地址
7. 状态信息

### 4.7 路由模型

路由模型用于支撑跨节点解析，其核心内容包括：

1. 目标节点编码
2. 下一跳节点编码
3. 下一跳地址
4. 跳数
5. 版本号

### 4.8 审计模型

审计模型用于记录关键业务事件，主要字段包括：

1. 操作时间
2. 操作类型
3. 标识
4. 操作人
5. 节点信息
6. 请求摘要
7. 结果摘要

## 5. 后端模块划分设计

### 5.1 标识管理模块

主要职责：

1. 注册标识
2. 校验标识
3. 查询标识
4. 更新元数据
5. 删除标识

### 5.2 资源管理模块

主要职责：

1. 创建上传会话
2. 完成上传
3. 直接绑定工具/服务资源
4. 查询资源
5. 删除资源
6. 生成下载签名地址

### 5.3 节点与拓扑模块

主要职责：

1. 节点注册
2. 节点握手
3. 相邻节点状态探测
4. 节点拓扑查询
5. 路由同步

### 5.4 解析与搜索模块

主要职责：

1. 本地解析
2. 跨节点解析
3. 批量解析
4. 本地搜索
5. 全网搜索

### 5.5 审计模块

主要职责：

1. 审计日志落库
2. 审计日志条件查询
3. 分页返回审计结果

### 5.6 认证集成模块

主要职责：

1. 解析认证中心令牌
2. 拦截写操作
3. 向前端提供登录态协作基础

## 6. 关键流程设计

### 6.1 标识注册流程

1. 前端提交注册请求。
2. 后端校验输入。
3. 调用 SDK 生成标识。
4. 保存元数据。
5. 写入审计记录。
6. 返回结果。

设计要点：

1. 节点地区码和机构码由节点环境决定，不允许用户任意篡改。
2. 行业、类别、注册类型等采用受控枚举。

### 6.2 文件资源绑定流程

1. 创建上传会话。
2. 返回上传地址或上传参数。
3. 客户端上传文件到对象存储。
4. 调用完成上传。
5. 后端校验上传会话和资源类型。
6. 生成资源记录并与标识绑定。
7. 提供后续下载签名能力。

设计要点：

1. 上传会话只用于文件资源。
2. 工具和服务资源不应强制走上传流程。
3. 数据库存储对象定位信息，不直接存储大文件。

### 6.3 工具/服务绑定流程

1. 用户填写资源类型和定位地址。
2. 系统创建资源记录。
3. 标识解析时一并返回资源信息。

设计要点：

1. 工具与服务不是“下载对象”，而是“可访问能力”。
2. 前端展示方式需要和文件资源区分。

### 6.4 单条解析流程

1. 接收标识。
2. 判断是否本地归属。
3. 本地查询数据库。
4. 若本地未命中，则走路由查找。
5. 通过 DRIRP 请求远端节点。
6. 汇总并返回结果。

设计要点：

1. 本地优先。
2. 远端解析带有链路标识和防环参数。
3. 失败时返回统一错误码和链路上下文。

### 6.5 批量解析流程

系统保留两种批量解析策略：

#### 6.5.1 迭代式

1. 入口节点扫描标识列表。
2. 按目标节点进行分组。
3. 对每组发起远端批量调用。
4. 汇总返回结果。

特点：

1. 控制集中
2. 便于统计
3. 适合实验对比

#### 6.5.2 递归式

1. 当前节点根据标识目标不断向下或向外转发。
2. 子节点继续递归处理。
3. 结果逐层返回。

特点：

1. 更贴近层级节点分布式解析思路
2. 有利于体现多层节点组织方法

### 6.6 搜索流程

1. 接收关键字和过滤条件。
2. 本地搜索。
3. 若为全网搜索，则向其他节点转发。
4. 汇总结果。
5. 返回候选列表供进一步解析。

### 6.7 审计流程

1. 接口进入业务处理前获取请求上下文。
2. 业务成功或失败后记录审计事件。
3. 审计查询按条件分页返回。

### 6.8 认证流程

1. 用户登录认证中心。
2. 获取 JWT。
3. 前端保存令牌。
4. 写接口请求自动附加令牌。
5. 后端拦截器校验通过后进入业务逻辑。

## 7. 多节点架构设计

### 7.1 节点层级设计

系统采用层级化节点结构，逻辑上可对应：

1. 根节点
2. 省级节点
3. 市级节点
4. 县级节点

该设计适用于论文中表达“分布式分层组织方式”。

### 7.2 节点启动与接入流程

1. 子节点启动。
2. 向父节点发送注册请求。
3. 父节点记录直连关系。
4. 子节点进行握手。
5. 父节点更新状态为激活。
6. 路由信息向上同步。

### 7.3 节点状态探测

当前重点采用相邻节点探测机制：

1. 已知相邻节点地址
2. 定期探测其状态接口
3. 对未直连节点标记为“未观察”

这一设计符合当前系统“只对已连接节点做状态感知”的实际边界。

### 7.4 路由传播机制

1. 子节点成功接入后，父节点获得其可达信息。
2. 父节点向上级同步路由。
3. 上级继续传播。
4. 逐层形成可达路由表。

## 8. 接口设计原则

### 8.1 接口分类

系统接口分为以下几类：

1. 业务接口
2. 节点接口
3. 审计接口
4. 认证接口
5. MCP 接口
6. 研究编排接口

### 8.2 设计原则

1. 接口语义清晰
2. 输入输出统一
3. 错误码一致
4. 读写分离
5. 前端页面流程和接口职责对应

### 8.3 写接口保护原则

1. 默认保护写操作
2. 读操作保持开放，便于演示和研究场景使用
3. 不在当前阶段引入复杂 RBAC

## 9. 数据存储设计概述

### 9.1 关系数据库

关系数据库负责存储结构化业务信息，包括：

1. 标识元数据
2. 资源记录
3. 上传会话
4. 节点与路由
5. 审计日志
6. 字典数据

### 9.2 对象存储

对象存储负责保存文件型资源实体，关系数据库中只保留其定位信息和必要元数据。

### 9.3 搜索增强存储

搜索增强目前采用轻量实现，保留后续迁移至独立向量引擎的空间。

## 10. 性能设计

### 10.1 线程与执行器隔离

系统将不同类型任务放入不同执行器中：

1. `resolveExecutor`
2. `searchExecutor`
3. `vectorSyncExecutor`

作用：

1. 避免相互阻塞
2. 提升整体稳定性
3. 为后续性能调优提供清晰切入点

### 10.2 连接池与连接复用

1. 数据库访问依赖连接池。
2. DRIRP 出站连接支持复用。
3. 避免高频短连接导致额外开销。

### 10.3 资源存储策略

大文件不入数据库，统一放入对象存储。这一策略能有效降低数据库 I/O 压力，提高后端可维护性。

## 11. 安全与治理设计

### 11.1 认证设计

1. 用户统一通过认证中心登录。
2. 后端仅负责验签和拦截。
3. 写接口必须带令牌。

### 11.2 审计设计

1. 关键操作统一记录。
2. 查询支持按标识、时间和类型筛选。
3. 审计逻辑尽量低耦合，不侵入核心业务流程。

### 11.3 节点通信安全扩展

系统预留以下能力，但可按需启用：

1. 消息鉴权
2. 时间戳校验
3. 随机数防重放

## 12. 可扩展性设计

### 12.1 外部标识映射

系统以本标识体系为主，但可后续增加“主标识 -> 外部标识”的映射关系，用于兼容其他体系。

### 12.2 搜索增强扩展

后续可替换当前轻量搜索方案，接入：

1. 更强的嵌入模型
2. 独立向量引擎
3. 混合检索能力

### 12.3 智能体接入扩展

现阶段通过 MCP 和 DeepResearch 展示开放能力，后续可扩展更多代理系统或自动化工作流平台。

## 13. 部署设计概述

### 13.1 本地联调部署

当前系统支持本地 6 节点联调，适合：

1. 多节点解析测试
2. 搜索验证
3. 中期答辩演示

### 13.2 独立服务部署

认证中心、MCP、DeepResearch 和业务后端均可独立启动，便于分模块排障和逐步部署。

## 14. 概要设计总结

本系统概要设计围绕“统一标识、统一建模、多节点组织、跨节点解析、开放接入”五条主线展开，形成了如下结构：

1. 用 `dris-java-sdk-next` 承载核心规则
2. 用 `drirp-java-sdk` 承载节点通信
3. 用 `dris-enterprise-backend-v2` 承载业务流程
4. 用 `dris-auth-center` 提供统一认证
5. 用 `dris-mcp-server` 和 `dris-deepresearch-*` 承载上层开放与展示

该设计既保证了当前原型系统可实现、可测试、可演示，也为后续详细设计、数据库设计、性能优化和论文系统设计章节提供了明确基础。
