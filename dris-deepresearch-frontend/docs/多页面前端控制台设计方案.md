# DRIS 多页面前端控制台设计方案

## 1. 设计目标

本方案面向 `dris-system-deploy-20260310` 的整体演示与答辩场景，目标是把现有前端从单一 DeepResearch 页面，扩展为一个能够完整展示 DRIS 系统能力的多页面控制台。

前端需要覆盖的能力包括：

1. 节点拓扑与跨节点状态展示
2. 标识注册、标识校验、标识查询、元数据维护、删除
3. 注册成功后的资源绑定、上传完成、版本查看、下载地址生成
4. 本地搜索、全局搜索、批量解析
5. 审计查询与治理证据展示
6. MCP 工具链访问与联调能力展示
7. DeepResearch 智能研究流程展示
8. 认证中心登录、令牌和用户信息展示

## 2. 业务主线纠偏

按你的业务逻辑，主流程不是“先做一堆生命周期操作，再考虑资源”。

而是：

1. 先注册标识
2. 注册成功后立刻进入资源绑定
3. 对于 `resource` 类型，再继续执行上传会话、COS 上传、completeUpload
4. 对于 `tool/service` 类型，则直接完成组件绑定

所以前端主业务页不应该设计成一个宽泛的“生命周期操作集合页”，而应该设计成：

1. `标识接入页`：严格承载“注册 -> 绑定”主流程
2. `标识管理页`：用于对已存在标识做查询、校验、更新、删除、版本和下载访问

这两者语义不同：

- `标识接入` 是新增接入流程
- `标识管理` 是存量对象维护流程

## 3. 总体方案

### 3.1 方案结论

采用一个统一前端工程，作为系统控制台。

不建议为每个节点单独开发一套前端，原因如下：

1. 代码重复，后期维护成本高
2. 页面功能基本一致，只是目标节点不同
3. 答辩展示时更适合一个统一入口
4. 节点差异属于运行时上下文，不是产品拆分问题

因此，推荐方案为：

1. 保留现有 `dris-deepresearch-frontend` 作为基础工程
2. 将其扩展为 DRIS 控制台，而不是仅保留研究页面
3. 在顶部增加全局节点切换器
4. 通过路由拆分为多个页面
5. 所有页面默认读取当前选中的节点地址作为后端 API Base URL
6. DeepResearch、MCP、认证中心作为独立页面接入

### 3.2 部署方式

前端保持单独部署，统一访问。

推荐本地联调方式：

- 前端：`http://127.0.0.1:5176`
- 认证中心：单独地址
- MCP：`http://127.0.0.1:38082`
- 编排服务：`http://127.0.0.1:38083`
- 六个后端节点：`8200` 到 `8205`

前端内部通过“节点切换器”决定当前访问哪个后端节点。

### 3.3 路由模式

推荐前期使用 `hash` 路由。

原因：

1. 本地 Vite 启动最简单
2. 后续部署到轻量服务器或静态目录时，不依赖额外 Nginx rewrite 配置
3. 答辩现场更稳，不容易出现刷新 404

## 4. 设计原则

### 4.1 低耦合

前端不直接耦合某一个节点。

所有与后端地址相关的行为，都通过统一的运行时上下文提供：

- 当前节点编码
- 当前节点后端地址
- 当前 MCP 地址
- 当前编排服务地址
- 当前认证中心地址

页面内部不硬编码端口。

### 4.2 高内聚

每个页面只负责一类能力展示：

- 节点页面只关心节点拓扑和状态
- 标识接入页只负责注册与资源绑定主流程
- 标识管理页只负责已有标识的查询、维护与访问
- 搜索页只关心检索与跨节点解析
- 审计页只关心治理与可追踪能力
- 研究页只关心 DeepResearch

### 4.3 可演示性优先

这是毕设系统，前端设计要服务于演示链路。

所以页面设计除了满足功能，还要满足以下要求：

1. 首页能快速说明系统整体结构
2. 每个页面都有明确“输入-执行-结果”三段式布局
3. 支持复制标识、复制节点地址、导出报告等答辩友好操作
4. 重点信息卡片化，少做纯表格堆叠

### 4.4 不改动后端业务逻辑

本次前端设计以复用现有后端 API 为主，不要求为前端额外改业务逻辑。

如果后续发现某些页面缺少聚合接口，可以再补轻量查询接口，但不先动核心流程。

## 5. 信息架构

推荐一级导航如下：

1. 总览
2. 节点拓扑
3. 标识接入
4. 标识管理
5. 搜索解析
6. 审计中心
7. 研究工作台
8. MCP 工具台
9. 认证中心

其中：

- `标识接入` 是系统主业务入口
- `标识管理` 是存量标识运维入口
- `研究工作台` 保留现有 DeepResearch 主要能力
- `MCP 工具台` 用于展示 MCP 作为能力接入层的作用

可选增强页面：

- `资源治理页`，仅在后期需要跨标识资源总览时再增加，不作为第一阶段必做项

## 6. 全局布局设计

### 6.1 应用壳层

整体使用“三段式壳层”：

1. 左侧导航栏
2. 顶部全局状态栏
3. 主内容区域

### 6.2 顶部状态栏内容

顶部统一展示：

1. 当前节点选择器
2. 当前节点级别与编码
3. 后端连通状态
4. MCP 连通状态
5. 编排服务连通状态
6. 当前登录用户或令牌状态
7. 快捷入口按钮

### 6.3 节点切换器

建议内置默认节点清单：

- `1100ROOT -> http://127.0.0.1:8200`
- `1100PROA -> http://127.0.0.1:8201`
- `1100CITA -> http://127.0.0.1:8202`
- `1100CNTA -> http://127.0.0.1:8203`
- `1100CITB -> http://127.0.0.1:8204`
- `1100CNTB -> http://127.0.0.1:8205`

节点切换后：

1. 当前页面数据重新加载
2. 与后端相关的 API Base URL 统一切换
3. MCP 和编排服务地址默认不变，但允许单独覆盖

## 7. 页面设计

### 7.1 总览页

页面目标：快速展示系统整体在线状态和关键入口。

核心模块：

1. 系统总状态卡片
2. 六节点在线状态卡片
3. 当前节点基础信息
4. 路由快照摘要
5. 标识接入、搜索解析、审计、研究四类快捷入口
6. 最近一次研究结果摘要
7. 关键指标面板

建议对接接口：

- `GET /api/v2/node/direct-descendants/status`
- `GET /api/v2/node/routes`
- `GET /api/v2/ops/metrics`
- 编排服务 `GET /health`
- MCP `GET /health`
- 认证中心 `GET /auth/public-key`

### 7.2 节点拓扑页

页面目标：展示多节点体系结构、父子节点关系、状态探测结果、路由信息。

页面分区：

1. 节点关系图
2. 直连下级节点列表
3. 路由表列表
4. 节点状态探测结果
5. 下线通知操作区

建议对接接口：

- `GET /api/v2/node/direct-descendants`
- `GET /api/v2/node/direct-descendants/status`
- `GET /api/v2/node/routes`
- `POST /api/v2/node/shutdown`

### 7.3 标识接入页

页面目标：

严格承载“注册成功后立即资源绑定”的主流程展示。

这一页建议设计成强顺序向导，而不是松散页签。

建议步骤如下：

1. 填写标识注册信息
2. 提交注册，返回 identifier
3. 自动进入资源绑定步骤
4. 根据组件类型选择绑定模式
5. 完成绑定并展示结果摘要

其中第 4 步按资源类型分支：

1. `resource`：创建 upload session -> 用户上传到 COS -> 调用 completeUpload -> 生成 component
2. `tool`：直接填写工具资源描述 -> 调用 component upsert
3. `service`：直接填写服务资源描述 -> 调用 component upsert

这一页的关键不是“功能很多”，而是要体现流程连续性：

- 注册成功后不能让用户再回主菜单自己找绑定页
- 前端应自动把新 identifier 带入下一步
- 最终给出“标识 + 组件 + 版本/访问信息”的接入完成摘要

建议对接接口：

- `POST /api/v2/identifiers/register`
- `POST /api/v2/identifiers/{identifier}/upload-sessions`
- `POST /api/v2/upload-sessions/{uploadId}/complete`
- `PUT /api/v2/identifiers/{identifier}/component`
- `GET /api/v2/identifiers/{identifier}/component`
- `GET /api/v2/identifiers/{identifier}/component/versions`
- `POST /api/v2/downloads/presign`

页面结果区建议展示：

1. 新生成的 identifier
2. metadata 摘要
3. digital object 摘要
4. 当前 component 摘要
5. 当前版本号
6. locator 或预签名下载地址

### 7.4 标识管理页

页面目标：

针对“已经存在的标识”，提供查询、校验、元数据维护、组件查看、版本查看、下载访问、删除能力。

这页不是主接入流程，而是存量运维页。

建议页面模块：

1. 标识查询框
2. metadata 查看与更新
3. exists / validate 快速校验
4. digital object 查看
5. component 查看与替换
6. version 历史查看
7. 下载地址生成
8. 删除确认区

建议对接接口：

- `GET /api/v2/identifiers/{identifier}/validate`
- `GET /api/v2/identifiers/{identifier}/exists`
- `GET /api/v2/identifiers/{identifier}/metadata`
- `GET /api/v2/identifiers/{identifier}/object`
- `PUT /api/v2/identifiers/{identifier}/metadata`
- `PATCH /api/v2/identifiers/{identifier}/metadata`
- `GET /api/v2/identifiers/{identifier}/component`
- `PUT /api/v2/identifiers/{identifier}/component`
- `DELETE /api/v2/identifiers/{identifier}/component`
- `GET /api/v2/identifiers/{identifier}/component/versions`
- `GET /api/v2/identifiers/{identifier}/component/versions/{versionNo}`
- `POST /api/v2/downloads/presign`
- `DELETE /api/v2/identifiers/{identifier}`

### 7.5 搜索解析页

页面目标：展示从自然语言或关键词输入，到搜索结果和跨节点解析结果的主业务链路。

左侧输入区：

1. 自然语言查询
2. 搜索模式选择 `KEYWORD / SEMANTIC / HYBRID`
3. 搜索策略选择 `ITERATIVE / RECURSIVE`
4. 锚点节点选择
5. limit、ttl、fanout 等参数

右侧结果区：

1. 搜索结果列表
2. 命中对象详情
3. 元数据批量解析结果
4. 数字对象批量解析结果
5. 资源批量解析结果
6. 跨节点访问路径说明

建议对接接口：

- `POST /api/v2/search`
- `POST /api/v2/search/global`
- `POST /api/v2/identifiers/resolve/batch/distributed`
- `POST /api/v2/identifiers/resolve/batch/object/distributed`
- `POST /api/v2/identifiers/resolve/batch/component/distributed`

### 7.6 审计中心页

页面目标：展示系统的治理与可追踪能力。

页面模块：

1. 条件筛选区
2. 分页结果表格
3. 操作类型分布统计
4. 单个标识时间线视图

建议对接接口：

- `GET /api/v2/audit/identifier-history`

### 7.7 研究工作台页

页面目标：保留现有 DeepResearch 作为系统的高阶能力展示页。

展示内容：

1. 研究问题输入
2. 智能体规划
3. MCP 工具调用时间线
4. 结构化报告
5. LLM 流式摘要
6. 证据卡片

建议继续对接：

- 编排服务 `GET /health`
- 编排服务 `GET /api/llm/models`
- 编排服务 `POST /api/research/run`
- 编排服务 `POST /api/research/stream`
- MCP `GET /health`

### 7.8 MCP 工具台页

页面目标：明确展示 MCP 不是后端本体，而是面向智能体的能力接入层。

页面模块：

1. MCP 连接状态
2. 工具列表
3. 工具输入参数面板
4. 原始返回结果面板
5. 结构化结果摘要面板

建议展示工具：

- `resolve_metadata`
- `resolve_object`
- `resolve_component`
- `batch_resolve_metadata_distributed`
- `batch_resolve_object_distributed`
- `batch_resolve_component_distributed`
- `search_global`
- `query_audit_logs`
- `get_node_routes`

### 7.9 认证中心页

页面目标：补齐用户、令牌、userinfo、公钥等认证链路展示。

页面模块：

1. 用户注册
2. 用户登录
3. token 获取结果
4. userinfo 查询
5. 公钥展示
6. token 缓存区

建议对接接口：

- `POST /auth/register`
- `POST /auth/login`
- `POST /oauth2/token`
- `GET /auth/userinfo`
- `GET /auth/public-key`

## 10. 页面间联动设计

建议支持以下联动：

1. 总览页点击某个节点，跳转到节点拓扑页并自动选中该节点
2. 标识接入完成后，自动跳转到结果摘要或标识管理页
3. 搜索结果点击某条标识，跳转到标识管理页并自动加载详情
4. 搜索解析页选中若干标识后，跳转到研究工作台并自动填入 identifiers
5. 审计页点击某条 identifier，跳转到标识管理页或研究工作台

## 11. 答辩演示推荐主线

建议按以下顺序：

1. 打开总览页，说明六节点整体在线情况
2. 进入节点拓扑页，展示路由与直连节点状态
3. 进入标识接入页，注册一个新标识
4. 注册成功后继续在同页完成 resource 或 service 绑定
5. 展示接入完成摘要
6. 进入搜索解析页，执行全局搜索与批量解析
7. 进入审计中心页，展示该标识的操作审计记录
8. 进入研究工作台页，输入问题生成研究报告
9. 最后打开 MCP 工具台或认证中心页，说明系统开放性与完整性

## 13. 本方案对现有前端的改造结论

结论如下：

1. 现有前端不需要推倒重来
2. 现有 DeepResearch 页面作为 `研究工作台页` 保留
3. 需要新增路由和壳层，把单页改造成控制台
4. 需要新增节点上下文和服务状态上下文
5. 资源绑定并入“标识接入”主流程，不再作为一级并列页面
6. 已有标识的维护能力单独归入“标识管理页”

## 14. 后续实现建议

下一步实现时，优先顺序建议为：

1. 引入 `vue-router`
2. 拆出 `AppShell`
3. 将现有 DeepResearch 页面迁到 `modules/research`
4. 新增总览页与节点切换器
5. 先实现 `标识接入页` 的强顺序向导
6. 再补 `标识管理`、`搜索解析`、`审计`、`认证`、`MCP` 页面

## 15. 其他页面细化设计

本节用于回答一个很具体的实现原则：

- `DeepResearch` 页面当前效果已经较好，不作为本轮重构重点
- 当前重点是把其他页面补齐，并且让它们和现有研究页共存在统一壳层内

### 15.1 DeepResearch 页处理原则

`研究工作台页` 本轮不做大修，只做以下最小接入：

1. 从当前单页应用中迁入统一路由壳层
2. 共享全局节点上下文、MCP 地址、编排服务地址
3. 保留现有页面布局、流式输出、时间线、证据卡片和导出能力
4. 只做必要的中文文案统一和头部样式收口
5. 不重写其工作流、不重拆其核心组件、不改变现有交互主路径

也就是说，当前前端改造重点是：

- `研究工作台页保持基本稳定`
- `其他页面补齐后形成完整控制台`

### 15.2 总览页细化

总览页不承担复杂业务操作，主要承担“看板 + 快速入口”职责。

建议分成 6 个区块：

1. 系统总状态
2. 当前节点信息
3. 六节点在线状态
4. 路由与拓扑摘要
5. 最近业务摘要
6. 快捷入口区

建议卡片如下：

1. 当前节点编码、层级、地区、机构
2. 在线直连节点数
3. 路由记录数
4. 最近一次研究耗时
5. 最近一次搜索结果数
6. 研究页、标识接入页、搜索页快捷跳转

页面布局建议：

- 顶部 4 张大卡片
- 中部 2 列：左边节点状态，右边路由摘要
- 底部快捷入口和最近活动摘要

### 15.3 节点拓扑页细化

这一页需要承担两件事：

1. 展示拓扑
2. 承担“父节点注册下级节点”的运维动作

所以页面应该分为左右两栏：

左栏：拓扑与状态

1. 当前节点信息卡
2. 直连下级节点列表
3. 下级节点在线状态表
4. 路由表

右栏：节点运维操作

1. 新增下级节点
2. 启动配置结果
3. 等待子节点上线状态区
4. 下线通知操作区

其中“新增下级节点”不能理解成普通业务表单，而应该理解成：

- 当前节点作为父节点
- 在前端填写子节点基础信息
- 父节点返回子节点 bootstrap 配置
- 子节点部署后再回传 hello/heartbeat 变成 active

建议表单字段直接对应后端 `NodeRegisterRequest`：

1. `childNodeName`
2. `regionCode`
3. `orgCode`
4. `childDrirpUrl`

建议结果区直接展示 `NodeRegisterResponse`：

1. `childLevel`
2. `relationStatus`
3. `healthStatus`
4. `bootstrapConfig`

前端交互步骤建议：

1. 在当前节点页点击“注册下级节点”
2. 打开抽屉填写信息
3. 调用 `/api/v2/node/register`
4. 返回后展示启动配置
5. 提供“复制配置”“导出配置”按钮
6. 自动轮询下级节点状态
7. 当 `PENDING/UNKNOWN` 变成 `ACTIVE/ACTIVE` 时标记为接入完成

要点：

- 县级节点禁用“注册下级节点”按钮
- 不能把“接口调用成功”直接等价成“节点已上线”
- 节点注册入口应放在节点拓扑页，不单独做一级导航

### 15.4 标识接入页细化

这一页是最重要的业务页，应该做成明显的向导页，而不是普通表单页。

建议 5 步结构：

1. 填写标识注册信息
2. 注册成功并返回 identifier
3. 自动进入资源绑定
4. 完成上传或直接绑定
5. 展示接入结果摘要

页面布局建议：

左侧：步骤导航

1. 注册信息
2. 资源类型选择
3. 上传/绑定
4. 结果确认

右侧：当前步骤内容区

1. 注册表单
2. 绑定表单
3. 上传提示区
4. 完成结果区

根据绑定类型，分成三条子流程：

1. `resource`：注册 -> 创建上传会话 -> 外部上传 COS -> completeUpload -> 展示 component/version
2. `tool`：注册 -> 填写工具资源 -> upsert component -> 展示结果
3. `service`：注册 -> 填写服务资源 -> upsert component -> 展示结果

结果摘要必须同时展示：

1. identifier
2. metadata 摘要
3. digital object 摘要
4. component 摘要
5. 当前版本信息
6. locator 或下载入口

### 15.5 标识管理页细化

这页的职责是“查已有标识”，不是“新接入”。

建议使用“三栏式”结构：

左栏：检索区

1. identifier 输入
2. exists / validate 按钮
3. 最近访问记录

中栏：对象主信息

1. metadata 卡片
2. digital object 卡片
3. component 卡片

右栏：操作区

1. 元数据更新
2. 组件替换或删除
3. 版本列表
4. 下载地址生成
5. 删除标识

这个页面要强调“单对象运维感”，不要做成纯表格后台。

### 15.6 搜索解析页细化

这一页的重点不是复杂表单，而是“输入一次，看到完整解析链路”。

建议布局为：

上方输入带：

1. 自然语言查询框
2. 搜索模式
3. 策略模式
4. 锚点节点
5. 执行按钮

中部结果区：

1. 搜索结果卡片列表
2. 访问节点链路
3. 命中结果排序说明

下方解析区：

1. metadata 批量解析
2. digital object 批量解析
3. component 批量解析

这一页需要特别优化两个体验：

1. 清楚显示“本次访问了哪些节点”
2. 清楚显示“某个结果为什么排在前面”

如果后续要继续优化展示效果，可以在结果卡片中补：

1. 命中标签
2. 归属节点
3. 资源类型
4. 解析成功/失败状态

### 15.7 审计中心页细化

审计中心页不建议只做表格，需要兼顾“分页查询”和“时间线展示”。

建议分两块：

上半区：筛选与统计

1. identifier 条件
2. operation 条件
3. 时间范围
4. success 条件
5. 统计卡片

下半区：结果展示

1. 默认表格视图
2. 支持切换为单标识时间线视图

列表列建议包括：

1. identifier
2. operation
3. actorUserId
4. actorRole
5. success
6. message
7. createdAt

时间线模式适合答辩展示，可直接说明“某个标识被谁在何时进行了哪些动作”。

### 15.8 MCP 工具台页细化

MCP 页的目标不是好看，而是把“工具层”讲清楚。

建议布局：

左栏：工具列表

1. 搜索类工具
2. 解析类工具
3. 审计类工具
4. 路由类工具

中栏：参数输入区

1. 动态表单
2. JSON 原始参数编辑区

右栏：结果区

1. 结构化摘要
2. 原始响应 JSON
3. 最近调用记录

展示重点：

1. 前端如何连接 MCP
2. 调用的是哪些工具
3. 每个工具底层对应后端什么能力

### 15.9 认证中心页细化

认证页建议做成“链路演示页”，而不是做完整用户中心。

建议模块：

1. 用户注册卡片
2. 用户登录卡片
3. token 结果卡片
4. userinfo 查询卡片
5. 公钥展示卡片

建议交互：

1. 注册后自动填充登录表单
2. 登录成功后自动缓存 token
3. userinfo 请求自动带 token
4. 公钥固定展示在右侧说明区

重点不是权限系统，而是展示“系统具备认证链路”。

## 16. 推荐实现顺序调整

既然 `DeepResearch` 页面当前不大修，那么实现顺序应改成：

1. 壳层与路由
2. 顶部节点切换器
3. 总览页
4. 节点拓扑页
5. 标识接入页
6. 标识管理页
7. 搜索解析页
8. 审计中心页
9. MCP 工具台页
10. 认证中心页
11. 最后把现有 DeepResearch 页面平滑迁入 `/#/research`

这样风险最低，因为：

1. 不会先碰你当前最好用的研究页
2. 可以先把空白页面补齐
3. 研究页最后只做壳层接入和统一样式收口
